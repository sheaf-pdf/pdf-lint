# Changelog

## 0.1.0-alpha.1 (unreleased)

The first release, and an alpha: until a release says it's stable, any alpha may change the API, each saying here what changed and how code follows. A crate that depends on an alpha names it exactly, `=0.1.0-alpha.1`: cargo's default, `0.1.0-alpha.1`, takes any later alpha of 0.1.0 too. The crate's own unit tests don't build from its package, as they take their files, and qpdf as a second reader, from pdf-fixtures, which is never published (below); its doctests do.

- **The reader.** `read::document(file, &options)` reads a file in memory whole under `read::Options`: the header, `startxref`, the cross-reference tables and streams along their `/Prev` chain, and each object at its offset through pdf-objects' parser, a stream's data by its `/Length` when that ends at `endstream`; where the sections don't read, the objects found by scanning, the trailer saying why. Offsets count from the header (ISO 32000-2, 7.5.2), so a file with bytes before `%PDF-` reads as it would without them, and `Fault::HeaderAt` says where the header is. Every position a reading gives is a place in the file's bytes, as a span is: an entry's offset, a revision's place, a fault's byte, each section's place in `Reading::sections`. `Options::section` is such a position too. A `/Length` that's a reference is followed to the object listed at its number and generation, at an offset or in an object stream. A reference to a number listed at another generation is to no object (ISO 32000-2, 7.3.10), even where an object of its number and generation is written at the entry's offset. A chain of references isn't followed. Where the object a `/Length` refers to is itself a reference, no length reads. A cross-reference stream's `/Length` is read only where it's direct (7.5.8.2), as its rows are read before any object is listed. Where it's a reference, the data is found by `endstream`, and a `Fault::XrefLength` says so. An object stream's own `/Length` is never read from an object stream (7.5.7). Nor is that of the encryption dictionary or of a stream it refers to, or of a stream whose length's object stream has a `/Filter` or `/DecodeParms` that refers to another object. Nor is any in a file found by scanning. Where no `/Length` reads, the stream's data is found by `endstream`, and a `Fault::Length` says so. Cross-reference streams and object streams are decoded through pdf-filters, `/Filter` and `/DecodeParms` read as qpdf reads them, a stream to at most 256 MiB (`read::STREAM`) and a reading's streams to 1 GiB in all (`read::BUDGET`) by default, and the objects read from an object stream placed in its decoded data, which the `Document` keeps. An encrypted file is opened by the passwords its options give, each a pdf-crypt `Password` as typed, tried in each of its encodings in the empty password's place, through pdf-crypt's standard security handler, revisions 2 to 6; given none, by the empty password. The trailer's `/Encrypt`, and each reference in the dictionary it names, is followed as any reference is, to the object listed at its number and generation, so a reference to a number listed at another generation is to no object, the file read as not encrypted, and said. `Options::section` reads the file as of a cross-reference section, an update's revision before. It's a file opened as `Reading::open` opens it and read whole as `Reading::into_document` reads it (below), which in memory can't fail: the one convenience over them. What the reader had to choose how to read is a `Fault`, with its place (below).
- **Read a damaged file where it proves it is.** `Options::recovery`, a `read::Recovery`, says how a file is read where its sections or objects aren't where it says. `Recovery::Verified`, the default, reads a section or an object a little off only where the file proves where it is, as its docs say. Each recovery is one `Fault::Moved` or `Fault::Shifted` a section, and an object read elsewhere has `Origin::Shifted` or `Origin::Recovered`. `Facts::recovered` says whether a reading took one, with faults off too.
- **Read a damaged file as PDFium does.** `Recovery::Pdfium` reads a file as PDFium does, as of chromium/8125, for a caller that shows it as a viewer would. It scans the file where PDFium does, and `Trailer::unwritten` says why (`Unwritten::Loop`, `Misplaced` and `NoPages` among the reasons). Its docs say where it parts from PDFium. The repository's `tests/pdfium` beside the crate holds each case, and its `differ.tsv` says why `Recovery::Verified` reads one otherwise.
- **A scanned file's object streams read.** A file read by scanning lists the objects in the object streams the scan finds, once its security handler is open, at the open or by `Reading::unlock`. `Fault::Members` says how many were read.
- **An update after a recovered reading.** `write::Base::of` takes a reading under a recovery. The update's `/Prev` is where the newest section was read, and its section lists each object read elsewhere where it is. Such an object is never copied as its bytes.
- **Ids are pdf-objects' struct.** Every id, `ObjectId`, is pdf-objects' `struct ObjectId { number, generation }`: `Reading::ids`, `get` and `record`, `Document`'s objects, `Span::stream`, a fault's place, the writer's bodies `(ObjectId, Body)` and its renumberings, and each error's id. pdf-crypt's handler takes the pair `(u32, u16)`, and the reader and the writer convert at their calls to it.
- **One way in, the passwords in `Options`.** `read::Options<'a>` (`Options` at the root) is how a file is read: `limits`, a `Limits`; `section`, the cross-reference section a file is read as of, none for the newest; `flate`, the pdf-filters `Backend` its Flate streams inflate on, `MinizOxide` by default, which this crate's dependency on pdf-filters names, so every build has it, or `ZlibRs` with this crate's `zlib-rs` feature, which docs.rs builds its docs with; `passwords: &'a [Password<'a>]`, the passwords an encrypted file is opened by, every password's encodings that fit the file's revision tried before any password's others, as the owner's and then the user's, a wrong one leaving it locked, or plain where its strings and streams aren't encrypted, as no password would, borrowed for the open alone (a reading keeps none); and `faults`, whether faults are looked for (below). `Options::DEFAULT` is an `Options<'static>`: no password, faults looked for. `Reading::open(source, &options)` is the one way in, and `read::document` and `WithReading::new(source, &options)` take the same options. `Options` is `#[non_exhaustive]` and `Copy`, set on a copy of `Options::DEFAULT` (`let mut options = Options::DEFAULT; options.passwords = &given;`); its `Debug` prints each password as pdf-crypt's `Password(..)`, without its text, and it isn't `PartialEq`, as passwords compare nothing. `Limits`, `#[non_exhaustive]` and set on a copy of `Limits::DEFAULT`, holds the caps: a stream's decoded data (`read::STREAM`), a reading's streams in all (`read::BUDGET`), the sections along `/Prev`, 1,024 (`read::SECTIONS`), the cross-reference entries, no more than the file has bytes or 2²⁰ if that's more, and pdf-objects' limits on each object, values nested 256 deep (`read::NESTING`) and 2²⁵ values in one, an object of more an error. Beside them, a stream lists at most 25 filters (`read::FILTERS`), the reader's own cap and not one of `Limits`'. They're the same in every build, one under cargo-fuzz (`--cfg fuzzing`) among them, so a dependant's fuzz build reads as any other.
- **A reading on demand.** `Reading` (`read::Reading`, at the root too) opens a file from a `ByteSource`, a slice, a `Vec<u8>` or an `Arc<[u8]>` (or a reference, a `Box` or an `Arc` of one, a `dyn ByteSource` among them), its header, sections and trailer read and an encrypted file's security handler opened by the passwords its options give, or the empty password, given none (`open`), which aren't kept; or by another once it's open (`unlock`, given the `Encoded` bytes to try, which may be what a prompt gives and not UTF-8, its handler opened from what the reading kept, a scanned file's object streams and, under `Recovery::Pdfium`, its page tree read again: what it had read dropped, to be read again decrypted, and a reading no password given opens handed back as it was, with pdf-crypt's `Refused`: `Password`, where none of them opens it; and, for a security handler the reader can't open, `OtherHandler`, another handler's, `Version`, a `/V` and `/R` the standard handler isn't, or `Malformed`, a dictionary it can't take or an `/Encrypt` that isn't one, each in the words `Encryption::Unsupported` says; one whose strings and streams aren't encrypted, `Encryption::Plain`, is refused alike, and stays plain). Then it reads each object when it's first asked for, kept (`get`) or not (`object_unkept`, which gives the object's `Record` with it), and decodes each object stream once, when an object in it is first read, whichever thread asks; `Send` and `Sync`. `faults` gives what it found in what it has read, in the order the whole read says it; `ids` and `entries` (each number's `read::XrefEntry`) what the sections list; `record`, `facts`, `metadata`, `bytes` (the bytes at a span, an encrypted file's refused as written), `id` (a `SourceId`, its own, which each record it makes holds), `source` and `into_source` (the source it reads), and `into_document`, the rest read as the whole read reads it; and `to_document`, the same document with the reading kept beside it, what it kept cloned and the rest read without keeping it, its object streams decoded and kept, so that it hands out what the document doesn't hold, a stream's data among it, and a read the source fails keeps none of what it read unkept. `data` hands out a stream's data, read each time it's asked for and not kept, borrowed from bytes in memory where nothing's decrypted: in an encrypted file that opened, decrypted as an object stream's is, by the stream's own `/Crypt` filter, else as `/StmF` says, and an embedded file's without one of its own as the encryption dictionary's `/EFF` says, where it names a crypt filter (from `/V` 4, below which `/EFF` isn't read); but a cross-reference stream's, and the catalog's metadata stream's under `/EncryptMetadata false` unless its own `/Crypt` filter encrypts it, left as written; refused where it may be ciphertext the reader doesn't decrypt, in a file no password opened (but one whose streams aren't encrypted, where only a stream's own crypt filter or an embedded file's `/EFF` encrypts it) or whose security handler it can't open, a stream the encryption dictionary refers to, and an embedded file's without a crypt filter of its own where `/EFF` isn't a name. `decoded_within` gives it through its filters, read as an object stream's are, by pdf-filters, to at most the less of the limit it's given and `Limits::stream` (`usize::MAX` for the reading's cap alone), neither kept nor counted against the budget, for a reader with a budget of its own. A source that doesn't hold its bytes in memory is read by position, a window at a time from where each read starts, from its `first_window` (4096 bytes by default), doubled while what's read runs to the window's end where more of the file could change it, through pdf-objects' `Parser::window`, so that each read reads what it would of the whole file: the header from the file's start, `startxref` and the last `%%EOF` back from its end, each section at its offset, and each object at its own, its first window reaching a byte past the next listed offset, so that an object as it should be is one read; a file the reader scans for its objects is read whole for the scan. `FileBytes` is a file read so (`pread`, on Unix and Windows), its length and `Identity` taken as it's made: the file itself, by a handle it holds open, its device and inode on Unix or its volume serial number and file index on Windows (same-file's `Handle`), and its length and modification time, so `FileBytes::unchanged` tells a file changed in place and `Identity::of` a path that holds another file now, one made where the first was removed among them; `Identity` is `Clone`, and `FileBytes::identity` gives a reference to it, a clone of which holds the file open after the `FileBytes` is dropped; `Identity::of` opens the file to read, without waiting, so it needs leave to read it, and refuses a path that's neither a file nor a folder (a FIFO, a socket, a device) without opening it; one swapped in after the path's metadata is read is opened without waiting, and on Unix without becoming the process's controlling terminal, then refused by what its handle is. Elsewhere `Identity` is the length and modification time alone. Its calls fail with a `read::Error` (`Error` at the root): why the object doesn't read, kept with it; or the source not giving its bytes, never kept, so a call asked again reads again, an object's `/Length` by reference, an object stream's filters' values and its data, the metadata, the bytes at a span and a stream's data among them; or why a stream's data isn't handed out, or doesn't decrypt or decode cleanly, pdf-crypt's and pdf-filters' errors, which hold what did, and whose `Debug`, and so `read::Error::Decrypt`'s and `Decode`'s, gives its length, not its bytes, which may be plaintext: `Decrypt(Error { data: Some(23 bytes), fault: Padding })`. Read in any order and made a `Document`, a reading is the whole read, the same objects, faults in the same order and the same decoded data, so long as no stream it decodes reaches its budget, spent in the order streams are decoded; `read::document` reads every object so, in order, by the same code.
- **Past a limit, one answer, filtered or not.** `decoded_within` holds a stream without filters to its limit too, cut there and said as filter 0's `Fault::Limit` in pdf-filters' error (`read::Error::Decode`), the one fault of pdf-filters' the reader makes itself, as a filtered stream's decode says it, so that every consumer matches one answer for past a limit, never the data cut short as if it were whole. `read::Error::Decode`'s `Debug` gives the data's length, not its bytes, as pdf-filters' error's does.
- **A stream's data as a viewer takes it, from each.** `Reading`, `WithReading` and `Document` implement pdf-objects' `Streams`: `decoded(id, limit)` gives what decoded of a stream that decodes in part, as PDFium takes it, unless the limit stopped it, within the less of the limit and `Limits::stream`; and why it gives none, in a resolver's words, what its resolver says of the object first: past the limit, `Why::Limit`; past the reader's own cap on a stream's data where that's less than the limit, through more filters than it takes, or an object nested deeper or of more values than it parses, `Why::Capped`; a password not given, a handler the reader can't open, a stream the encryption dictionary refers to or data that doesn't decrypt, `Why::Locked`; a source that failed, `Why::Source`; a filter the reader doesn't take, or a `/Filter` or `/DecodeParms` it can't take as written, `Why::Filter`; what isn't a stream, isn't there, or fails to decode before it gives a byte, `Why::Damaged`, where a stream that decodes cleanly to nothing is given, empty. A `Reading`'s is owned, decoded for the call by `decoded_within`, and no method of a reading's shadows it: it's `reading.decoded(id, limit)` where the trait is in scope, or `Streams::decoded(&reading, id, limit)`. A `WithReading`'s is its reading's, of the stream its document holds, an object stream's too, decoded anew, so that it answers as its reading does at every limit. A `Document`'s is, of the object streams it holds that the reader decoded whole, their data, lent within the limit while their objects are as read; of a stream it holds as bytes, built or edited in memory and so in plain view, the data decoded as a reading decodes a stream, through `read::filters`, references followed through the document, Flate on the default backend, up to the less of the limit asked and `read::STREAM`, past the limit `Why::Limit` and past the cap `Why::Capped`, through a filter it doesn't take `Why::Filter`, its own `/Crypt` filter no filter, whatever it names, as `read::filters` reads one, the bytes being plaintext, which a writer encrypts as it writes them, so a document decrypts nothing, owned and not kept; and of any other stream, a span of a file the document doesn't hold, `Why::Detached`: a document alone holds the file's objects and not their data, which `WithReading` gives, and so of an object stream the reader cut off as it decoded it, at a fault, the stream's limit or the budget, or that didn't decrypt cleanly, as what it holds of one is what the objects in it are read from, not the stream's data; asked again it gives the same, where `Why::Source` is a source that failed to give them, which asked again may. A `&WithReading` is a `Resolve` too, its document's objects, so that what reads a file through a resolver and its streams, as a font does, reads it through a `&WithReading` alone. A stream's data has two readings, each naming the other: `Streams::decoded` as a viewer takes it, and `Source::decoded_within` the reader's own account, every fault of it, for a checker, which a document alone gives of no stream, so that a checker asking of one learns it of all, so not of a stream it holds as bytes either, whose data it gives a viewer; `Source` is a `Streams` (`trait Source: Streams`), so what's given a `&dyn Source` gives both, and a reader of one's own implements `Streams::decoded` beside `Source`'s methods.
- **A `Source`, which `Document`, `Reading` and `WithReading` are.** `Source` is the trait a reader of a file implements: `ids`; `get`, the object or why it doesn't read, an `Unread`; `trailer`; `header_version`; `faults`, a `Cow` of `(Place, Fault)` pairs in the whole read's order, lent or made for the call; `tell_faults(&mut dyn Sink<Fault>)`, provided, which tells them to any of pdf-objects' `fault::Sink`s in that order, none to one that wants none, so that one sink takes several crates' faults; and, each defaulting to nothing, so that a reader of its own implements what it knows: `size`, the file's length; `metadata`, the catalog's metadata stream's data where it's in plain view, an `Option<Cow<[u8]>>`; `record`, where an object was read; `held`, an object stream's decoded data as the reader holds it; `revisions`; `facts`; `in_the_clear`; and `decoded_within`, a stream's data decoded within a limit and decrypted as the reader decrypts it, which a reading and a `WithReading` give and a document alone doesn't: past the limit an `Error::Decode` holding what decoded, with `Fault::Limit`, and from a reader that gives no stream's data, none of any. `Reading<S>` answers of what it has read when it's asked: `ids` collected; `get` its own, a read the source of the file's bytes failed given as `Unread::Source { message }`, in the source's words, which asked again may read (its `Why` is `Source` through `Unread::unreadable`, and its `container` none); `faults` made for the call; `metadata` read on the way, none where the source fails; `size` and `facts` its own; `held` and `in_the_clear` of each object stream it has decoded, whose header read, and none and false of one it hasn't decoded yet or of a generation other than 0, which no object stream has; and `decoded_within` its own. A `Reading`'s and a `Document`'s own methods of the trait's names (`ids`, `get`, `faults`, `metadata`, `size`, `facts`, `decoded_within` and the rest) give the same answer in a plainer or a richer form, an iterator for a `Vec`, the reading's `Error` for an `Unread`, no `Option` where it always knows, a borrow for a `Cow`, and are what a call on one names; the trait's are reached through a `&dyn Source` or by the trait's name (`Source::get(&reading, id)`). `Unread::unreadable(id)` is the `Unreadable` that `Resolve::try_resolve` gives for object `id` that a `Source::get` gave `Unread` for, its `Why` `Damaged`, `Limit` or `Locked`, or `Source` for `Unread::Source`, as a `Document`'s and a reading's own say it, so that a resolver over any `Source` gives the same reasons; none where the file hasn't it, which `try_resolve` gives as no object.
- **What it reads into.** `Document`, a `Source` read whole, `#[non_exhaustive]`, made outside the crate by `Document::new`, its fields private: what it holds is read by its accessors, each of `Source`'s name and its answer in a plainer form where it always knows, `trailer()`, `header_version()`, `faults()`, `held(stream)`, `in_the_clear(stream)`, `size()`, `metadata()` (`Option<&[u8]>`), `facts()` (`&Facts`) and `revisions()`, and the document's own, which `Source` hasn't, `update()` (`Option<&Update>`) and `encryption()` (`&Encryption`); and what a reader outside the crate knows of a file it read is set by `trailer_mut()`, `set_header_version`, `set_update`, `set_size`, `set_metadata`, `set_encryption` and `set_revisions`. What the bytes reader keeps of its own reading, its faults, the object streams it decoded and those that leave their objects' strings in the clear, and its `Facts`, has no setter, its meaning being what that reader read: another reader's faults are its own to keep. `Trailer`, `#[non_exhaustive]`, made outside the crate by `Trailer::new`: the cross-reference stream it is, where it is one (`stream`), its dictionary or that stream (`object`, read by `dict` and changed by `dict_mut`), and why it isn't the newest section's trailer, where it isn't (`unwritten`, a `read::Unwritten`, below). `Update`, the file's newest incremental update, `#[non_exhaustive]`, made outside the crate by `Update::new`. `Encryption`, `#[non_exhaustive]`, whether the file is encrypted and whether it opened: `None`; `Opened`, `#[non_exhaustive]` too, by the owner's password or the user's (`owner`), which of those given in which encoding (`by`) and what its `/P` grants (`permissions`, below), made outside the crate by `Encryption::opened(owner)`, its `by` and `permissions` set by `Encryption::by` and `permitting`, and each field after them by a setter of its own (below), so that a field the variant gains changes no constructor; `Locked`; `Plain`, a file whose strings and streams aren't encrypted, `/Identity`, read whole all the same; and `Unsupported`, a handler the reader can't open, and why (`source::Unsupported`, below). Why an object doesn't read is an `Unread`, which `Source::get` and `Document::unread` give: it isn't in the file, doesn't parse (pdf-objects' `parse::Error`), or isn't the object at its offset; the object stream it's in doesn't decode (`read::Undecoded`, its filters `read::Unfiltered`), needs a password, doesn't read, isn't in the file, or doesn't say where it is (`read::Unindexed`); or it runs to where a fault cut the stream's data off; or the source didn't give its bytes (`Unread::Source`); or, from another reader, that reader's words (`Unread::Other`). Each is `#[non_exhaustive]` and derives `Display` and `std::error::Error` with thiserror, its `Display` the whole reason, with no `source`. `read::XrefEntry`, what a cross-reference section says of an object number, is `#[non_exhaustive]`, and its `Free` variant too, so it can say more; a `Reading` gives each number's (`entries`). `Document::record` gives where the bytes reader read an object that reads, and `records` each object's, a `Record`: the reading it was read in (`source`, its `SourceId`; two records are equal when they say the same of where their objects were read, whichever readings they're of, so two readings of one file are equal), the id it was read as (`id`), its `Origin` (at a section's offset, at a shift from it, found by a scan, or in an object stream, by its number, and where in it), its bytes (`at`) from `n g obj` to past `endobj` and whether `endobj` follows it, a stream's data's `DataExtent`, whether by its `/Length`, and whether that's a reference, and a hash of its bytes as read, private (below); and `Document::facts`, the `Facts` of the file as written: where `%PDF-` starts (`header_offset`), the newest section's offset and `XrefKind`, how many sections, whether one is a hybrid's, the largest cross-reference stream's number, whether a linearization holds, and whether a recovery was taken (`recovered`). Each is `#[non_exhaustive]`; another reader's `Document` has none and the defaults. pdf-objects, pdf-filters and pdf-crypt are re-exported whole, as `pdf_objects`, `pdf_filters` and `pdf_crypt`, and none of their items by name, so that their types are named through this crate at the versions the reader gives them (`pdf_structure::pdf_crypt::Password`, the `Encoded` bytes `unlock` takes and the `Refused` it gives, pdf-filters' error a `read::Error` holds): each is a public dependency, whose version moves with this crate's. The root has `Error`, `Fault`, `Options`, `Limits`, `Reading`, `WithReading`, `ByteSource`, `FileBytes`, `Identity`, `Prefix` and `SourceId` of `read`'s, and `source`'s types. `&Document` and `&Reading<S>` implement pdf-objects' `Resolve`, which what follows references reads through, from any thread: a reference resolves to its object, read and kept as `get` keeps it, or to none, null, where the file hasn't it, it doesn't read, or the source fails the read (which keeps nothing, so asked again it reads), without the `Unread` that `get` would clone to say why. `try_resolve`, pdf-objects', says why where it's asked, cloning nothing for an object that reads: none where the file hasn't it, or an `Unreadable` of the object, its `Why` and `get`'s words after the object's number: `Limit` for a value nested too deep or of too many values and for an object stream with too many filters, `Locked` for an object stream a password is wanted for or that doesn't decrypt, as an object in one that nothing decodes is, `Source` for a read the source failed, as `Error::Io` says, the kind of what its object stream doesn't read by for an object in it, and `Damaged` for the rest. `Reading::failed_resolves` counts the resolves the source failed, by either way of asking, on the failing path alone, so what reads through `resolve`, which has no reason to give, can learn that some were: `get`'s failure tells its caller and isn't counted. Every `Unread` and `Undecoded` is held to its kind by a test, and one that `Unread` grows has to choose.
- **A document in memory.** A `Document`'s objects are private, each kept with its record while it's as read, so a record is always of the object beside it: read by `contains` (whether it's listed, read or not), `objects` (each that reads, by number), `range` (those in a range of ids) and `unread` (each that doesn't, with why), beside `Source`'s `ids` and `get`; and written by `set` (an object put in, with no record, giving back the one it replaces; one of another file put in unplaced, by pdf-objects' `Object::unplace`, a stream's data given first as its bytes, as its places would be read as this file's, by a check and by the writer), `insert` (`set` at generation 0), `set_unread` (what a reader outside the crate puts where an object doesn't read), `remove` (the object and its record) and `get_mut` (an object to edit, its record dropped, as a `&mut` can replace it whole without an edit's dropping its span). An object stream it holds decoded is lent as its data (`Streams::decoded`) only while its object is as read: put (`set`, `insert`, `add`), taken to edit (`get_mut`, `get_dict_mut`, `catalog_mut`), set unread or removed, it isn't; the objects read from it keep their places in its data, which `held` gives. The metadata a document read (`metadata`) is the catalog's metadata stream's alike, given while that stream is the one it was read from and as read: put, taken to edit, set unread or removed, or the catalog or the trailer's `/Root` leading to another, it's none; what `set_metadata` sets is given as set. A document numbers new objects (`new_id`, and `add`, which puts one at it): past every number the file's cross-references list, in use, in an object stream or free, past its cross-reference streams' (`Facts::max_stream`) and the trailer's `/Size` less one, where that's a number below the largest (a `/Size` of 2^32 or more is passed over, so that alone never takes new ids past every number), or for one built, past its `/Size` less one, never 0; and past every number put in since, read or not, so each `new_id` gives another though none is set. its numbers past its `/Size`, every number listed and its cross-reference streams'), refused for one read by scanning, one without `/Root`, and a reading as of an earlier revision (`Options::section`); `Base::new` one a caller read otherwise, its fields set after; `Base::holds` whether a file is still the one it describes, as long and ending in the same section. Each write gives back a `write::Written` (`#[non_exhaustive]`): its section (where each object landed), where it starts, its `/Size`, its `/ID` and the file as it now is, a `Base` for an update after it. A stream's data where the reader read it (`Data::At`) is read from the reading given (`write::ReadFrom`, sealed, a `Reading` as `&dyn ReadFrom`), only at its own number there, decrypted and encrypted again as the write is; elsewhere, or with no reading, refused (`write::Error::Placed`). An update is encrypted as its file is, by that file's encryptor, told by where its dictionary is, the dictionary as the file stores it where the base knows it (`Base::of`'s reading's; `Base::new`'s trailer's where it's direct), the `/ID[0]` its key is made from, and the key itself, by a check of it (pdf-crypt's `KeyCheck`, compared in constant time) that `Base::of` keeps of its reading's handler and each write gives back of its encryptor's, so that a dictionary made to give one key by the owner's password and another by the user's passes neither reading's encryptor for the other's (`Unmatched` otherwise: another file's whose `/Encrypt` is at the same number and whose `/ID[0]` is the same among them, and any after a `Base::new` whose trailer names the dictionary by number, until `Base::encryption` is set); where an encryptor's keys are made per object (RC4, AES-128, told by pdf-crypt's `Method`), `Encryptor::of` keeps the numbers its reading lists free, each with the generation its entry gives, and an object at one is refused in an update and a whole file alike (`Free`), and a whole file lists each free at that generation, `/Size` past it, so that a tool that follows its free list takes none at a deleted object's key. A whole file has one section, whose `/Encrypt` is the only one, so it encrypts what it's given at a number its reading named `/Encrypt` by in an earlier section, or where the write moves the dictionary from, as any object; and leaves what the dictionary refers to out of object streams, as a reader reads it before it has a key. The writer's own objects (object streams, a cross-reference stream, a new encryption dictionary) pass over the numbers what's written refers to and doesn't hold, so that a reference to no object, which reads as null, doesn't come to name one. Refused, with nothing written, beside those: a number 0 or past `NUMBERS` (`Number`), one given twice (`Twice`), and in an update, another object given at the number of one it passes over, an object as read that the file holds there already, at any generation (`Twice`), so that none replaces it without a word; an object at the encryption dictionary's number (`EncryptAt`), a table asked to pack (`PackedTable`), no number left for an update's stream (`NoNumber`), a base read by scanning, without `/Root` or of an earlier revision (`Unsound`, `Rootless`, `Earlier`), a catalog not given nor read where `/EncryptMetadata false` needs it to say which stream is the metadata (`Catalog`), a group naming a number not packed or one twice (`Group`), a write a flag stops (`Options::stop`, `Stopped`), a stream's data or a source's bytes that don't read (`Data`, the reading's error in words; `Io`, the I/O error's `kind` and its words). - **Copies renumbered in place.** Under a renumbering, an object as read (`write::Body::Read`) is copied as the bytes it was read from but its header, `n g obj`, where it's written at another number, and each reference the renumbering names otherwise, `n g R` or `null`, each written anew where its bytes had it: a comment between a changed reference's tokens goes with them, and every other byte, strings and stream data among them, is copied as it was. ### Security

- **A copy's check can't be steered.** The hash a `Record` holds of its object's bytes is std's keyed hash, under one key for the process from std's `RandomState`. The key is never shown, so bytes changed on purpose can't be made to hash as they did. Two readings in one process still hash the same bytes alike. On a target where std has no randomness from the operating system (`wasm32-unknown-unknown`), the key can be guessed. `Record`'s `Debug` leaves the hash out.
- **A written file's `/ID` by SHA-256.** `write::file_id`, which `write::full` and `write::update` call, makes a file's second `/ID` string the first 16 bytes of SHA-256 of what's written. The same bytes write the same `/ID`, and the string says nothing else of the file. The first string, which an RC4 or AES-128 key is made from, is kept.
- **A recovery is proven by bytes alone.** A crafted file can put an `n g obj` where a shift lands, inside another object's string say, or where a scan finds it, and it's read in its place. Each such recovery is a fault, so a checker that reads them sees it.
- **One damaged file, two readings.** `Recovery::Verified` and `Recovery::Pdfium` can read one damaged file as two documents, as two viewers can. A checker that reads under `Verified` and reports its faults flags a file a viewer may show otherwise. `Facts::recovered` tells it with faults off too.
