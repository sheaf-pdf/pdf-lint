# Changelog

## 0.1.0 (unreleased)

- **The reader.** `bytes::read` reads a file from its bytes: the header, `startxref`, the cross-reference tables and streams along their `/Prev` chain, and each object at its offset through pdf-objects' parser, a stream's data by its `/Length` when that ends at `endstream`; where the sections don't read, the objects found by scanning, the trailer saying why. Cross-reference streams and object streams are decoded through pdf-filters, `/Filter` and `/DecodeParms` read as qpdf reads them, a stream to at most 256 MiB (`bytes::STREAM`) and a reading's streams to 1 GiB in all (`bytes::BUDGET`) by default, and the objects read from an object stream placed in its decoded data, which the `Document` keeps. `bytes::read_opened` opens an encrypted file with the passwords given, each a `Password` as typed, tried in each of its encodings in the empty password's place, through pdf-crypt's standard security handler, revisions 2 to 6; `bytes::read` with the empty password. `bytes::read_from` and `read_from_opened` read the file as of a cross-reference section, an update's revision before. What the reader had to choose how to read is a `Warning`, with its object and where.
- **A reading on demand.** `Reading` (`bytes::Reading`, at the root too) opens a file from a `ByteSource`, a slice, a `Vec<u8>` or an `Arc<[u8]>` (or a reference, a `Box` or an `Arc` of one, a `dyn ByteSource` among them), its header, sections and trailer read and an encrypted file's security handler opened by the empty password (`open`) or by the passwords given (`open_with`, every password's encodings that fit the file's revision tried before any password's others, a wrong one leaving it locked, or plain where its strings and streams aren't encrypted, as no password would), which aren't kept, or by another once it's open (`unlock`, given the `Encoded` bytes to try, without reading the file again: what it had read dropped, to be read again decrypted, and a reading no password given opens handed back as it was, with pdf-crypt's `Refused`); then reads each object when it's first asked for, kept (`get`) or not (`object_unkept`, which gives the object's `Record` with it), and decodes each object stream once, when an object in it is first read, whichever thread asks; `Send` and `Sync`. `warnings` gives what it warned of in what's read, in the order the whole read says it; `record`, `facts`, `entries`, `metadata`, `bytes` (the bytes at a span, an encrypted file's refused as written), `id` (a `SourceId`, its own, which each record it makes holds), `source` and `into_source` (the source it reads) and `into_document`, the rest read as the whole read reads it; and `to_document`, the same document with the reading kept beside it, what it kept cloned and the rest read without keeping it, its object streams decoded and kept, so that it hands out what the document doesn't hold, a stream's data among it, and a read the source fails keeps none of what it read unkept. `data` hands out a stream's data, read each time it's asked for and not kept, borrowed from bytes in memory where nothing's decrypted: in an encrypted file that opened, decrypted as an object stream's is, by the stream's own `/Crypt` filter, else as `/StmF` says, and an embedded file's without one of its own as the encryption dictionary's `/EFF` says, where it names a crypt filter (from `/V` 4, below which `/EFF` isn't read); but a cross-reference stream's, and the catalog's metadata stream's under `/EncryptMetadata false` unless its own `/Crypt` filter encrypts it, left as written; refused where it may be ciphertext the reader doesn't decrypt, in a file no password opened (but one whose streams aren't encrypted, where only a stream's own crypt filter or an embedded file's `/EFF` encrypts it) or whose security handler it can't open, a stream the encryption dictionary refers to, and an embedded file's without a crypt filter of its own where `/EFF` isn't a name. `decoded` gives it through its filters, read as an object stream's are, by pdf-filters, to at most the limit on a stream, neither kept nor counted against the budget. A source that doesn't hold its bytes in memory is read by position, a window at a time from where each read starts, from its `first_window` (4096 bytes by default), doubled while what's read runs to the window's end where more of the file could change it, through pdf-objects' `Parser::window`, so that each read reads what it would of the whole file: the header from the file's start, `startxref` and the last `%%EOF` back from its end, each section at its offset, and each object at its own, its first window reaching a byte past the next listed offset, so that an object as it should be is one read; a file whose sections don't read is read whole, to be scanned. `FileBytes` is a file read so (`pread`, on Unix and Windows), its length and `Identity` taken as it's made: the file itself, by a handle it holds open, its device and inode on Unix or its volume serial number and file index on Windows (same-file's `Handle`), and its length and modification time, so `FileBytes::unchanged` tells a file changed in place and `Identity::of` a path that holds another file now, one made where the first was removed among them; `Identity` is `Clone`, and `FileBytes::identity` gives a reference to it, a clone of which holds the file open after the `FileBytes` is dropped; `Identity::of` opens the file to read, without waiting, so it needs leave to read it, and refuses a path that's neither a file nor a folder (a FIFO, a socket, a device) without opening it. Elsewhere `Identity` is the length and modification time alone. Its calls fail with a `bytes::Error`: why the object doesn't read, kept with it; or the source not giving its bytes, never kept, so a call asked again reads again, an object's `/Length` by reference, an object stream's filters' values and its data, the metadata, the bytes at a span and a stream's data among them; or why a stream's data isn't handed out, or doesn't decrypt or decode cleanly, pdf-crypt's and pdf-filters' errors, which hold what did. Read in any order and made a `Document`, a reading is the whole read, so long as no stream it decodes reaches its budget, spent in the order streams are decoded; `bytes::read` and the rest read every object so, in order, by the same code. The limits are one value, `Limits`, in a reading's `Options` (with the section a file is read as of, and `flate`, the pdf-filters `Backend` its Flate streams inflate on: `MinizOxide` by default, which this crate's dependency on pdf-filters names, so every build has it, or `ZlibRs` with this crate's `zlib-rs` feature, which docs.rs builds its docs with), both `#[non_exhaustive]`, set on a copy of their `DEFAULT`; `bytes::SECTIONS`, `STREAM`, `BUDGET` and `NESTING` are the defaults' values.
- **What it reads into.** `Source`, the trait a reader of a file implements; `Document`, a `Source` read whole, `#[non_exhaustive]`, made outside the crate by `Document::new`; `Trailer`, `#[non_exhaustive]`, made outside the crate by `Trailer::new`; `Warning`, `#[non_exhaustive]`, made by `Warning::new`; `Update`, the file's newest incremental update, `#[non_exhaustive]`, made outside the crate by `Update::new`; and `Encryption`, `#[non_exhaustive]`, whether the file is encrypted and whether it opened, its `Opened` variant `#[non_exhaustive]` too, saying by the owner's password or the user's, and which of those given in which encoding (`by`), made outside the crate by `Encryption::opened(owner)` and given its `by` by `Encryption::by`, a setter for each field, so that a field the variant gains changes no constructor. Why an object doesn't read is an `Unread`, which `Source::get` and `Document::unread` give: it isn't in the file, doesn't parse (pdf-objects' `parse::Error`), or isn't the object at its offset; the object stream it's in doesn't decode (`bytes::Undecoded`, its filters `bytes::Unfiltered`), needs a password, doesn't read, isn't in the file, or doesn't say where it is (`bytes::Unindexed`); or it runs to where a fault cut the stream's data off; or, from another reader, that reader's words (`Unread::Other`). Each is `#[non_exhaustive]` and derives `Display` and `std::error::Error` with thiserror, its `Display` the whole reason, with no `source`. What a reader says of the file it read stays text, as any reader fills it: `Trailer::unwritten`, `Encryption::Unsupported` and each `Warning`. `bytes::XrefEntry`, what a cross-reference section says of an object number, is `#[non_exhaustive]`, and its `Free` variant too, so it can say more; a `Reading` gives each number's (`entries`). `Document::record` gives where the bytes reader read an object that reads, and `records` each object's, a `Record`: the reading it was read in (`source`, its `SourceId`; two records are equal when they say the same of where their objects were read, whichever readings they're of, so two readings of one file are equal), its `Origin` (at a section's offset, recovered by the scan, or in an object stream, by its number, and where in it), its bytes (`at`) from `n g obj` to past `endobj` and whether `endobj` follows it, and a stream's data's `DataExtent`, whether by its `/Length`, and whether that's a reference; and `Document::facts`, the `Facts` of the file as written: where `%PDF-` starts (`header_offset`), the newest section's offset and `XrefKind`, how many sections, whether one is a hybrid's, the largest cross-reference stream's number, and whether a linearization holds. Each is `#[non_exhaustive]`; another reader's `Document` has none and the defaults. A `Document`'s objects are private, each kept with its record while it's as read, so a record is always of the object beside it: read by `contains` (whether it's listed, read or not), `objects` (each that reads, by number), `range` (those in a range of ids) and `unread` (each that doesn't, with why), beside `Source`'s `ids` and `get`; and written by `set` (an object put in, with no record, giving back the one it replaces), `insert` (`set` at generation 0), `set_unread` (what a reader outside the crate puts where an object doesn't read), `remove` (the object and its record) and `get_mut` (an object to edit, its record dropped, as a `&mut` can replace it whole without an edit's dropping its span). `Document::decoded` stays public: an object stream member's record names its bytes there, so it says where the object was read only while they're as read. pdf-objects, pdf-filters and pdf-crypt are re-exported as `pdf_objects`, `pdf_filters` and `pdf_crypt`, and pdf-crypt's `Password`, `Encoded` and `Encoding` at the root, so their types are named at the versions the reader gives (a reading's `bytes::Error` holds pdf-filters' error where a stream's data doesn't decode cleanly, and `unlock` pdf-crypt's `Refused`): each is a public dependency, whose version moves with this crate's. The root has `bytes::Error` (as `Error`), `SourceId`, `Reading` and the rest of what a reading takes and gives. `&Document` and `&Reading<S>` implement pdf-objects' `Resolve`, which what follows references reads through, from any thread: a reference resolves to its object, read and kept as `get` keeps it, or to none, null, where the file hasn't it, it doesn't read, or the source fails the read (which keeps nothing, so asked again it reads), without the `Unread` that `get` would clone to say why.
- **A document in memory.** A `Document`, built by `Document::new` or read whole, numbers new objects (`new_id`, and `add`, which puts one at it): past every number the file's cross-references list, in use, in an object stream or free, past its cross-reference streams' (`Facts::max_stream`) and the trailer's `/Size` less one, where that's a number below the largest (a `/Size` of 2^32 or more is passed over, so that alone never takes new ids past every number), or for one built, past its `/Size` less one, never 0; and past every number put in since, read or not, so each `new_id` gives another though none is set. Once they reach 4,294,967,295, the largest number, as a file that lists it or an object put there can, each is the next number above the last handed out that no entry holds (or, where an object put at the largest took them there, above where they'd have started), from 1 again after the largest, so it may be one the file lists free, and once they've gone round, one handed out before and not set since. `max_id` is the number they start after, and `set_max_id` sets it, never below a number held. Two documents are equal where their objects, records and fields are, and their new ids start at one number. `dereference` follows a chain of references to where it ends, as many as 128, giving the last id on the way, none where one names an object that isn't there or doesn't read, or the chain loops; `get_dict` gives an object's dictionary, or its stream's, through the references it is, and `get_dict_mut` to change, an edit of the object it ends at, dropping its record; `catalog` and `catalog_mut` the trailer's `/Root`'s; `Trailer::dict_mut` the trailer's dictionary, or its cross-reference stream's, to change, one that's neither made an empty dictionary first. `reachable` gives every id the trailer reaches, through the objects that read, each once, in the order found (the trailer's references, then each found object's in turn, each in the order written, every entry of a key written twice among them), an id of an object that isn't there or doesn't read found and not followed; `prune` removes every object it doesn't reach, read or not, with its record, and gives their ids by number: object streams and cross-reference streams go, as nothing refers to them, so `Trailer::stream` may name an object no longer held, and the encryption dictionary stays, as the trailer refers to it; `decoded` is left as it is.
- **Sections and object streams written.** `write` writes what a file's structure is written in, for a caller that lays the file out, its objects written by pdf-objects' writer, each where the output has got to. `Section` is a cross-reference section's entries by number, each an `Entry` (in use at a position and generation; free, to be used next at a generation; or the `index`th object in an object stream): a whole file's (`Section::full`, one subsection from 0, every number it doesn't list written free, the free entries linked in a list from entry 0) or an update's (`Section::append`, runs of the numbers it lists, after a file whose header starts where it's given); built by `insert` (an entry for 0, the free list's head, passed over), with `size`, its `/Size`, `lists`, and `get`, what it lists a number as, so where each object landed; written as a table (`table`, which refuses an object in an object stream, `write::Error::Packed`, and an offset past ten digits, `TooFar`) or as a stream (`stream`, listing itself, its `/W` as narrow as its widest field, a whole file's deflated under PNG's Up predictor, `/Predictor 12`, an update's as it is), then `startxref`. Positions are counted from the header, as PDFium, pdf.js and qpdf read them, where ISO 32000-2 and this crate's reader count them from the file's start (7.5.4), which differ only for an update of a file with bytes before its header; a position before the header is refused (`BeforeHeader`). `packable` says whether an object may go in an object stream (7.5.7): not a stream, an object whose generation isn't 0, an encryption dictionary (a `/Filter` name, `/O` and `/U`), the linearization dictionary, nor a signature dictionary (a `/Type`, or with none an `/FT`, of `/Sig` or `/DocTimeStamp`; with neither, `/ByteRange` and `/Contents`). `container` makes an object stream of objects written direct, a header of each one's number and where it starts from `/First`, each followed by a newline, deflated, its `/Length` direct; none where its data would be past `MAX_DATA`, `Limits::stream`'s default, 256 MiB, so the reader reads every container the writer makes whole (`fits`). `MEMBERS`, 100, is the most a container holds where a writer chooses, qpdf's default; `NUMBERS`, 8,388,607, the most objects a file may hold (ISO 32000-1, Annex C), below which a written file's numbers are, which also keeps any two from sharing an RC4 or AES-128 object key. Both deflate through pdf-filters' `encode`, by the backend and at the level a `Deflate` says, `#[non_exhaustive]` and set on a copy of `Deflate::DEFAULT`, miniz_oxide at 6, which every build has (zlib-rs with the `zlib-rs` feature). What can't be written is refused, with nothing written: `write::Error`, `#[non_exhaustive]`, deriving `Display` with thiserror, the whole message, and no `source`, holding pdf-objects' writer's refusal (`Serialize`), of a trailer that can't be written among them, and pdf-filters' (`Unencodable`).
- **For tests** (the `fixtures` feature, hidden): files written from objects, whole with a cross-reference table or stream or assembled from bytes written by hand, and encrypted by pdf-crypt's `writer`, or as a new file is, under the handler and dictionary pdf-crypt's `Handler::create` makes from a generator the caller passes; and qpdf, the program `PDF_LINT_QPDF` names or `qpdf` on the `PATH`, run as a second reader of a file and as a decoder to set the reader's decoding beside, a stream decoded alone handed to it in a file of its own, which tempfile makes in the temp folder and removes after. For this workspace's tests and fuzz targets, not for a user: without it, nothing runs a program, reads `PDF_LINT_QPDF` or writes a file.
- **From pdf-lint.** These are pdf-lint 0.2.0's reader, its `bytes` and `source` modules and the `/Filter` reading under them, what they do unchanged (but that each object is read through pdf-objects' parser and is pdf-objects' `Object`, whose value an edit changes, dropping its span; that each string keeps the `Form` it was written in, which stands in for `Source::hex` and `Document::hex`, gone; that a stream's data is a `Data`, `Data::At` where it was a span; that `Value::Stream` holds a `Box<Stream>`; and that a `Document`'s objects are private, each kept with where it was read, through methods, where pdf-lint's were a public map), which pdf-lint re-exports where they were. Each warning and error says what pdf-lint 0.2.0's said, word for word (why an object doesn't read is an `Unread`, where pdf-lint's was a `String`, and `Trailer`, `Update`, `XrefEntry` and `Encryption::Opened` are `#[non_exhaustive]`, where pdf-lint's weren't), but that an object of more than 2^25 values is an error, which is new, and that the reader's limits are the same in a build under cargo-fuzz (`--cfg fuzzing`), where pdf-lint's were smaller, so a dependant's fuzz build reads as any other, and a token nested past `bytes::NESTING` that can't start a value is the error it is, where pdf-lint said it was nested too deep. Rust 1.85 builds it.
