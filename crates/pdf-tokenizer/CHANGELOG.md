## 0.2.0 (2026-11-06)

A breaking release. 0.1.1 was never published: what it held is under this release too, after the breaking changes.

- **Breaking: `Kind` is one byte, and whether a string closed is on its token.** `Kind::String { closed }` and `Kind::HexString { closed }` are `Kind::LiteralString` and `Kind::HexString`, with no fields, and `Token` has a fourth public field, `closed: bool`: false only for a literal or hexadecimal string whose closing delimiter didn't come, true for every other token, the ones `eol`, `space_byte`, `data` and `data_until` make included. `Kind` is `#[repr(u8)]`, a tag of one byte a table can be indexed by (`kind as usize`), and `Kind::ALL` lists every kind in that order, so the table has an entry a kind; a `Token` is still `Copy`, and still four words on 64-bit targets. A match on either string kind drops its `{ .. }`, one on `{ closed: false }` reads `token.closed` instead, and a `Token` built by its fields names `closed`. `String` is renamed so that `use Kind::*` shadows nothing, and so that the two kinds pair as ISO 32000-2 names them (7.3.4.2, 7.3.4.3), beside `decode::literal` and `decode::hex`.
- **Breaking: `NumberError::Underflow`.** `decode::number` and `Token::number` read a real whose digits aren't all zero but reads as zero, such as `0.` followed by 400 zeros and a `1`, as `Err(Underflow)`, "a number too small to hold", where they read `Ok(0.0)`; `0.0` and `-0.0`, and a real of zeros however long, are still `Ok`, to the bit. A match on `NumberError` without a wildcard gains an arm. `decode::integer` and `Token::integer` can't underflow. The fuzz target holds `number` to Rust's reading of its text with the new error where that reading is zero from a digit that isn't.
- **Breaking: `How` is `#[non_exhaustive]`.** A match on it outside the crate needs a wildcard: a quirk is found in files, not designed, so one may come in a minor release. `How::ALL`, every `How` in the order of their discriminants, the ordinary ones first, is public, a slice (`&[How]`), so its length is no part of the type.
- **Exhaustive on purpose: `Kind`, `NumberError` and `decode::pdfium::Number`.** They stay exhaustive, so that a match on every kind, every error, or every form of a number PDFium holds, is checked by the compiler; a new variant of any is a breaking release. The README says so.
- **`Quirks` is a set to build and read.** `Quirks::insert`, `len` and `iter` (a `QuirksIter`: the quirks in `How::ALL`'s order, its length exact), `Quirks::EMPTY`, the set of none as a `const`, so a set is built in a constant, `|` and `|=` of two sets, `collect` and `extend` from `How`s, and `for how in quirks`; `contains` and `is_empty` as before. A `How` that isn't a quirk (`How::is_quirk`) is ignored, as `Pieces::quirks` has always done. So a reader gathers the quirks of many pieces into one set, or asks a set what it holds, with nothing collected. No `Display`: the crate gives bytes and kinds, never words.
- **`size_hint` on the decoders, so a buffer is reserved once.** `Pieces::size_hint` is a piece at least while bytes are left and at most one a byte; `Pieces::bytes` carries the upper bound, and so does `decode::pdfium::Bytes`: a value is never longer than the bytes decoded, which each now says, so `Vec::with_capacity` of the upper bound holds it without growing, where a reader decoded twice to size a buffer to the byte. `Pieces` is a `FusedIterator`, and `bytes()` gives a `decode::Bytes`, a type of its own as `decode::pdfium::Bytes` is, so a reader can hold it in a struct or name it in a signature, `Clone` and fused. The fuzz target holds every hint, the tokenizer's included, to what follows, each step costing a byte at least.
- **Bytes without their opener are the inside of a value already open.** `decode::literal` given bytes that don't start with `(` reads them as the inside of a string already open: a `(` among them nests, a `)` that balances no `(` closes the string, and what follows is invalid. `literal(b"a(b)c")` is five plain bytes, where it was a `)` closing a string never opened and an invalid `c`; `literal(b"a)b")` is `a`, a closing delimiter and an invalid `b`, where the `)` was plain. `name` and `hex` read so already (`name(b"abc")` three plain bytes; `hex(b"4142")` two escapes, `hex(b">")` a close), and the three say so. `Token::verbatim` follows on such bytes. A token's pieces don't change: a token has its opener.
- **The significant tokens, and the structure's, as iterators.** `Tokenizer::significant()` is `next_significant()` repeated and `skimming()` is `skim()` repeated, each an iterator (`Significant`, `Skimming`: named types, fused, `size_hint` at most a token a byte) that borrows the tokenizer and advances it: a loop over one can stop, with `take_while` or a `break`, and the tokenizer goes on from there by any step, `next_significant`, `skim`, `eol` or `data_until`, as a reader mixes them on one cursor. Iterating the tokenizer itself still gives every token, the white-space and comments included, so the tokens join back into the input. The fuzz target holds each view to its step.
- **A keyword told, and the input and what's left of it.** `Token::is_keyword(word)`: whether a token is the keyword `word`, its kind and its bytes together, so a name or a string of the same bytes isn't, which every reader that looks for `obj`, `R` or `endstream` had written for itself. `Tokenizer::input()`, the whole input, and `remaining()`, what's left of it from the next token's offset to the end, so a reader needn't carry the slice beside the tokenizer, and so it can read what's left itself (`remaining().len()` is `size_hint`'s upper bound).
- **What's dropped by mistake is marked, and what can be `const` is.** `#[must_use]` on `Tokenizer`, `Pieces`, `QuirksIter` and `decode::pdfium::Bytes`, which do nothing until asked, and on every function whose result dropped is a mistake and whose type doesn't say so itself: `offset`, `rules`, `input`, `remaining`; `Token::end`, `range`, `is_keyword`, `pieces`, `verbatim`; `Pieces::quirks`; `How::is_quirk`; `Quirks::contains`, `is_empty`, `len`; `Rules::is_white_space`, `is_regular`, `RuleSet::rules`; `is_white_space`, `is_delimiter`, `is_regular`; `decode::pdfium::number`, `real`, `Number::float`, `integer`. `Tokenizer::new`, `at`, `offset`, `input` and `remaining`, and `Token::end` and `range`, are `const fn`, beside `Quirks`' and the byte classes', so a tokenizer at an offset can be made at compile time. `decode::integer`, `number`, `Token::integer` and `Token::number` say which error each gives, and when.
- **`#[inline]` on the small entry points.** `Tokenizer::new`, `at`, `offset`, `rules`, `input`, `remaining`, `next`, `next_significant`, `eol`, `space_byte`, `data` and `data_until`, and `Token::end`, `range` and `is_keyword`, carry `#[inline]`: a hint, never `always`, so a consumer built without link-time optimization can inline a call a token where it chooses to, and one built with it loses nothing. Measured through a reader over a large file under both kinds of build, flat, and the binary slightly smaller; a content scanner built with thin link-time optimization and one codegen unit read a few per cent slower on one measure, which by instructions is the same work placed differently: its instruction counts are within 1% of the build without the hints, and its cycles swing by that much between builds whose code is identical, so the hints stay. **`next` alone is `#[inline(always)]`:** with the hint, a consumer built without link-time optimization keeps `Tokenizer<Iso>::next` and `Tokenizer<Pdfium>::next`, what `new` and `at` give, out of line, a call a token that returns the token through memory, and reads them at half the speed of the same loop over a `Tokenizer<Rules>`, whose `next` it inlines; forced, the four read alike (the crate's benchmarks: 2x on every token of objects and of a content stream, 1.5x on a reader's loop), a consumer built with link-time optimization is unchanged to the instruction, and its binary is a few kilobytes larger.
- **Benchmarks.** `cargo bench -p pdf-tokenizer` times the tokenizer and the decoders on inputs the benchmarks make as they run, the same on every run: every token of objects and of a content stream, each repeated to about 4 MB; the objects as a reader takes them, with the end of line and the data after each `stream`; nested arrays and dictionaries passed by `next_significant` and by `skim`; a stream of 32 MB scanned by `data_until` to its marker, and one with no marker; a long literal string, one with escapes, and a long hexadecimal string, each tokenized and its value's bytes counted, and the plain one's value borrowed as written; and names with escapes, integers and reals decoded, by ISO 32000-2's reading and PDFium's. Each run of tokens is under four sides, ISO 32000-2's rules and PDFium's, fixed in the type and chosen as the tokenizer runs; throughput is in bytes. So a change to the tokenizer is judged before and after it. The harness is criterion, a dev-dependency never built for a user of the crate, and `benches/` is outside the package.
- **The package and the API, checked before a publish.** CI packages the crate as a publish would (`cargo publish --dry-run`, in a target directory of its own made fresh each time, so a stale build can't pass or fail it) and checks what the package holds: `src/`, the README, the CHANGELOG, the manifest and the lock, nothing else, no benchmark among them; and it checks the public API against the version published on crates.io with cargo-semver-checks, so a break the version doesn't allow fails before it's published. The README's licence links are the repository's URLs, which reach the files from crates.io and docs.rs, where a path beside the crate reached nothing, and a test holds them to that. The manifest names the crate's documentation (docs.rs) and a fifth keyword, `iso-32000`.
- **Docs.** `Kind::Space` says its two sources (a maximal run from the iterator; one end of line from `eol`, one byte from `space_byte`); `Kind::Data` says why it's a kind the iterator never yields (a `Vec<Token>` can then hold a whole file, its streams' data included); `Tokenizer::at` and `offset` say that an offset past the end is taken as the end, so a reader at any offset never fails. The README says what a literal string that never closes costs a recovery that tokenizes from many offsets (the rest of the input at each), and the remedy, a bounded slice. A clone looking ahead, and `Tokenizer::size_hint`, each have a test. `Debug` of a `Tokenizer`, of `Pieces` and of either `Bytes` says where it is, the input's length or the bytes left, and its rules or syntax, not the input's bytes, which may be a whole file's.

What 0.1.1 held:

- **PDFium's rules, beside ISO 32000-2's.** `Tokenizer::with_rules(Pdfium)` reads by the rules PDFium's content and object parsers follow, from any offset, and `rules()` says which a tokenizer follows; `new` and `at` follow ISO 32000-2's, as before, and every token they give is the same. `Tokenizer` takes its rules as a type parameter defaulted to `Iso`, so `Tokenizer<'a>` is `Tokenizer<'a, Iso>`, what `new` and `at` give, and code that names it reads as before. `Iso` and `Pdfium` fix the rules in the type, with nothing to choose at each token, so ISO 32000-2's rules cost what they did; a `Rules` value chooses them as the tokenizer runs (`with_rules(Rules::Pdfium)`), at a branch a token, for a reader that learns only then which it wants. `RuleSet` is the sealed trait the three share. The rules part in three places: a word of digits, signs and points is a number (`--5` and `5-3` integers, `1.2.3` and `.` reals; `1e5` stays a keyword); a hex string runs to its `>` over any byte, unclosed only when the input ends first; and 0x80 and 0xFF are white-space. `Rules::is_white_space` and `Rules::is_regular` give a byte's class under each. Every promise holds under both, a slice's included, and the fuzz target and the unit tests check each set of rules, and the two side by side: from each token PDFium's rules read, ISO 32000-2's read the same token but where the rules part; and each set chosen as the tokenizer runs reads the tokens it reads fixed in the type. `Rules` is `#[non_exhaustive]`. Under PDFium's rules a hex string's pieces may hold `How::Invalid`, which the docs say.
- **PDFium's readings.** `decode::pdfium` reads what a token stands for as PDFium does, a value without pieces: `number` as PDFium holds a number (`Number::Unsigned` or `Signed`, 32 bits and 0 past them, or `Real`, the decimal a word starts with as an `f32`), with `float()` and `integer()` as PDFium reads one, and `real` the same decimal as an `f64`; `name`, a `#` before any two bytes an escape, a byte that's no hex digit read as 0; `literal`, an unescaped CR or CR LF as written, and an octal escape that an unclosed string ends inside as nothing; `hex`, the digits paired over any other byte. None fails, panics or allocates. `Token::pieces`, `verbatim`, `integer` and `number` stay ISO 32000-2's reading, whatever rules read the token. Each reading is held to PDFium as of chromium/8125, a development snapshot of PDFium: cases of each, a word shown or drawn, with PDFium's answer for each recorded at that build, which a test holds the readings and `Rules::Pdfium`'s tokens to without PDFium (the cases in the crate's `tests/`, not packaged). They read alike at chromium/7881 and chromium/8076, where they were first read.
- **Passing tokens.** `next_significant()` gives the next token that's neither white-space nor a comment, making no token of what it passes, and `skim()` the next that opens or closes an array or a dictionary, or a string that doesn't close, looking only at the bytes that could start one: from an opener, skimming on to the closer that balances it passes all it holds without reading it. Each gives what iterating on to the first such token finds, and leaves the tokenizer where that leaves it, under either rules; which closer closes which opener, and how deep they may nest, stay the caller's to say. The tests and the fuzz target hold both to the iteration they stand for, from every offset.
- **Faster, the tokens the same.** The byte classes are looked up in a table of 256 entries made when the crate is compiled, `is_white_space`, `is_delimiter` and `is_regular` still `const fn`. A comment's end, a literal string's parentheses and backslashes, a hex string's `>` by PDFium's rules and `data_until`'s marker are found with memchr, the crate's second dependency, its default features off so it needs only `core` (no `std`, no `alloc`; CI's build against `core` alone builds it), on SIMD where the target has it. Without `std`, memchr can't ask the processor what it has as it runs, so on x86-64 it searches with SSE2; an application with `std` gets AVX2 where the processor has it by turning on memchr's `std` feature, which depending on memchr with its default features does. Each token's remaining bytes are taken once, and its bytes sliced from them. `verbatim()` searches a value's bytes for what would need decoding instead of walking its pieces, the same answer from the same place for any bytes, which the fuzz target checks on every token. Each was kept where it measured faster, by both rules.
- **Numbers read by their bytes.** `decode::integer` and `Token::integer` read the digits themselves, toward the sign, where they took the word's text and Rust's reading of it; `decode::number` and `Token::number` read a decimal of 19 digits at most, no more than 2^53 without its point and at most 22 digits after it, by one division of exact values, which rounds as a decimal's reading does, and the rest as before; on x86 without SSE2, whose x87 division can round a quotient twice, every decimal is read as before. The same values and errors, to the bit, held by a test over every word of up to six digits, signs, points and letters and the edges of each, and by the fuzz target's body, which holds every number token's value to Rust's reading of its text.
- **Docs.** The byte classes cite ISO 32000-2's 7.2.3, where they're defined, not 7.2.2.
- **A slice of a file.** The crate docs and the README say what a reader that has read only part of a file can count on: only a token that reaches the end of the slice can come out otherwise with more bytes after it, and every token before it is the whole file's. The fuzz target checks it, the input cut where it chooses and tokenized in lockstep with the whole, without allocating; so do the unit tests, at every cut of their inputs. Nothing in the API changes.
- **thiserror, without `std`.** `NumberError`'s `Display` and `Error` are derived with thiserror 2, built with its default features off, each text as before; `NumberError` is still exhaustive. It's one of the crate's two dependencies (memchr, above, the other), and it still needs only `core`: CI builds it against `core` alone (`-Z build-std=core`), for a target with neither `std` nor `alloc`. Building it now builds thiserror's derive, and the crates under it (`syn`, `quote`, `proc-macro2`, `unicode-ident`), for the host.

## 0.1.0 (2026-10-25)

- **The tokenizer.** `Tokenizer::new` and `Tokenizer::at` iterate a byte slice's `Token`s (kind, offset, and bytes as written) from any offset, losslessly: the tokens join back into the input. `offset()` says where the next token starts (not `position()`, which on a `&mut Tokenizer` would be `Iterator::position`). Kinds follow ISO 32000-2's lexical conventions, and a run of regular bytes is a number only when it's written as one.
- **Data it can't measure.** `eol()` and `space_byte()` take the white-space after `stream` and `ID`, and `data(len)` and `data_until(marker)` take the data after it as one `Data` token.
- **Byte classes.** `is_white_space`, `is_delimiter` and `is_regular`.
- **Decoding.** `Token::pieces` splits a name, a literal string or a hex string into `Piece`s, each a run of the token's bytes with the value byte it stands for and `How`, so every escape and every reader-dependent choice can be seen where it was written. `Pieces::bytes` gives the value's bytes, never more than the token's, and `Token::verbatim` the value as written, borrowed from the input, when nothing in it needs decoding. Nothing allocates. `Token::integer` and `Token::number` give an `i64` or an `f64`. `decode::name`, `literal`, `hex`, `integer` and `number` do the same for bytes from elsewhere.
- **Tests.** Unit tests for each kind, a property test and a fuzz target that check every promise on every token, and an ignored test that checks a folder of PDFs (`PDF_TOKENIZER_CORPUS`).
