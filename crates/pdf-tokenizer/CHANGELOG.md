# Changelog

## 0.1.1 (unreleased)

- **PDFium's rules, beside ISO 32000-2's.** `Tokenizer::with_rules(Pdfium)` reads by the rules PDFium's content and object parsers follow, from any offset, and `rules()` says which a tokenizer follows; `new` and `at` follow ISO 32000-2's, as before, and every token they give is the same. `Tokenizer` takes its rules as a type parameter defaulted to `Iso`, so `Tokenizer<'a>` is `Tokenizer<'a, Iso>`, what `new` and `at` give, and code that names it reads as before. `Iso` and `Pdfium` fix the rules in the type, with nothing to choose at each token, so ISO 32000-2's rules cost what they did; a `Rules` value chooses them as the tokenizer runs (`with_rules(Rules::Pdfium)`), at a branch a token, for a reader that learns only then which it wants. `RuleSet` is the sealed trait the three share. The rules part in three places: a word of digits, signs and points is a number (`--5` and `5-3` integers, `1.2.3` and `.` reals; `1e5` stays a keyword); a hex string runs to its `>` over any byte, unclosed only when the input ends first; and 0x80 and 0xFF are white-space. `Rules::is_white_space` and `Rules::is_regular` give a byte's class under each. Every promise holds under both, a slice's included, and the fuzz target and the unit tests check each set of rules, and the two side by side: from each token PDFium's rules read, ISO 32000-2's read the same token but where the rules part; and each set chosen as the tokenizer runs reads the tokens it reads fixed in the type. `Rules` is `#[non_exhaustive]`; `Kind`, `Token` and `How` are unchanged, so under PDFium's rules a hex string's pieces may hold `How::Invalid`, which the docs now say.
- **PDFium's readings.** `decode::pdfium` reads what a token stands for as PDFium does, a value without pieces: `number` as PDFium holds a number (`Number::Unsigned` or `Signed`, 32 bits and 0 past them, or `Real`, the decimal a word starts with as an `f32`), with `float()` and `integer()` as PDFium reads one, and `real` the same decimal as an `f64`; `name`, a `#` before any two bytes an escape, a byte that's no hex digit read as 0; `literal`, an unescaped CR or CR LF as written, and an octal escape that an unclosed string ends inside as nothing; `hex`, the digits paired over any other byte. None fails, panics or allocates. `Token::pieces`, `verbatim`, `integer` and `number` stay ISO 32000-2's reading, whatever rules read the token. Each reading was held to PDFium 7881 and 8076 through one-page files.
- **Passing tokens.** `next_significant()` gives the next token that's neither white-space nor a comment, making no token of what it passes, and `skim()` the next that opens or closes an array or a dictionary, or a string that doesn't close, looking only at the bytes that could start one: from an opener, skimming on to the closer that balances it passes all it holds without reading it. Each gives what iterating on to the first such token finds, and leaves the tokenizer where that leaves it, under either rules; which closer closes which opener, and how deep they may nest, stay the caller's to say. The tests and the fuzz target hold both to the iteration they stand for, from every offset.
- **Faster, the tokens the same.** The byte classes are looked up in a table of 256 entries made when the crate is compiled, `is_white_space`, `is_delimiter` and `is_regular` still `const fn`. A comment's end, a literal string's parentheses and backslashes, a hex string's `>` by PDFium's rules and `data_until`'s marker are found with memchr, the crate's second dependency, its default features off so it needs only `core` (no `std`, no `alloc`; CI's build against `core` alone builds it), on SIMD where the target has it. Each token's remaining bytes are taken once, and its bytes sliced from them. `verbatim()` searches a value's bytes for what would need decoding instead of walking its pieces, the same answer from the same place for any bytes, which the fuzz target checks on every token. Each was kept where it measured faster, by both rules.
- **Docs.** The byte classes cite ISO 32000-2's 7.2.3, where they're defined, not 7.2.2.
- **A slice of a file.** The crate docs and the README say what a reader that has read only part of a file can count on: only a token that reaches the end of the slice can come out otherwise with more bytes after it, and every token before it is the whole file's. The fuzz target checks it, the input cut where it chooses and tokenized in lockstep with the whole, without allocating; so do the unit tests, at every cut of their inputs. Nothing in the API changes.
- **thiserror, without `std`.** `NumberError`'s `Display` and `Error` are derived with thiserror 2, built with its default features off, each text as before; `NumberError` is still exhaustive. It's one of the crate's two dependencies (memchr, above, the other), and it still needs only `core`: CI builds it against `core` alone (`-Z build-std=core`), for a target with neither `std` nor `alloc`. Building it now builds thiserror's derive, and the crates under it (`syn`, `quote`, `proc-macro2`, `unicode-ident`), for the host.

## 0.1.0 (2026-10-25)

- **The tokenizer.** `Tokenizer::new` and `Tokenizer::at` iterate a byte slice's `Token`s (kind, offset, and bytes as written) from any offset, losslessly: the tokens join back into the input. `offset()` says where the next token starts (not `position()`, which on a `&mut Tokenizer` would be `Iterator::position`). Kinds follow ISO 32000-2's lexical conventions, and a run of regular bytes is a number only when it's written as one.
- **Data it can't measure.** `eol()` and `space_byte()` take the white-space after `stream` and `ID`, and `data(len)` and `data_until(marker)` take the data after it as one `Data` token.
- **Byte classes.** `is_white_space`, `is_delimiter` and `is_regular`.
- **Decoding.** `Token::pieces` splits a name, a literal string or a hex string into `Piece`s, each a run of the token's bytes with the value byte it stands for and `How`, so every escape and every reader-dependent choice can be seen where it was written. `Pieces::bytes` gives the value's bytes, never more than the token's, and `Token::verbatim` the value as written, borrowed from the input, when nothing in it needs decoding. Nothing allocates. `Token::integer` and `Token::number` give an `i64` or an `f64`. `decode::name`, `literal`, `hex`, `integer` and `number` do the same for bytes from elsewhere.
- **Tests.** Unit tests for each kind, a property test and a fuzz target that check every promise on every token, and an ignored test that checks a folder of PDFs (`PDF_TOKENIZER_CORPUS`).
