# Changelog

## 0.1.0-alpha.1 (unreleased)

The first release, and an alpha: until a release says it's stable, any alpha may change the API, each saying here what changed and how code follows. A crate that depends on an alpha names it exactly, `=0.1.0-alpha.1`: cargo's default, `0.1.0-alpha.1`, takes any later alpha of 0.1.0 too.

- **The handler.** `Handler::open` takes a `Dictionary`, the encryption dictionary's values typed, the file's first `/ID` element and passwords, each an `Encoded` (below), and opens it by the first that's the owner's or the user's (or the empty password, given none): revisions 2 to 4 (Algorithms 2 to 7), 5 (Adobe's Extension Level 3) and 6 (Algorithms 2.A, 2.B, 11, 12), with `/Perms` checked (Algorithm 13). It tries those whose encoding fits the dictionary's revision first, the rest after, each in the order given; one whose bytes the revision takes as it took one tried before (padded or cut to 32 bytes for 2 to 4, cut to 127 for 5 and 6) isn't tried again, as it gives the same key, and for 5 and 6 costs no hash. `Handler::opened_by` says which opened it: its index among those given and its encoding, none for the empty password tried as none was given. Short `/O` and `/U` are filled out with zeros, revision 5's and 6's long ones cut short, a `/V 2` key's `/Length` taken in 40 to 128 bits, as qpdf reads them; a dictionary is refused (`Refused`), saying why, for the first of these it has: no `/Filter` (`Malformed`); another security handler's (`OtherHandler`, its `/Filter`'s name as written: the public-key handler's, say); a `/V` and `/R` the standard handler isn't (`Version`, the pair, a later handler's revision told by `r`); `/O` or `/U` missing or too long, or another value it can't take (`Malformed`, why in words, a dictionary that's wrong); then no password that opens it (`Password`). `Dictionary` and `CryptFilter` are `#[non_exhaustive]`, so a field can come without a breaking release: outside the crate, one is made from `default()`, its fields set after.
- **Decrypting.** `decrypt_string` and `decrypt_stream` decrypt for object `n g` by its crypt filter (`/StmF`, `/StrF`, a stream's own by `named`): RC4 and AES-128 with each object's key (Algorithm 1), AES-256 with the file's (1.A). An `Error` has what decrypted, if anything, and its `Fault`: AES ciphertext with no whole block past its IV, a part block past the whole ones (white-space there, as a recovered `/Length` leaves, is left off without a word), padding that isn't, a crypt filter's method that isn't one (`Fault::Method`, its name as written, said lossily as UTF-8), an AES key of the wrong length; and `Handler::faults`, `/Perms` that doesn't match.
- **A password as typed, and the bytes tried.** `Password` is a password's text; `Password::encodings` gives the bytes it may have been set as, each an `Encoded`, tagged with its `Encoding`: its SASLprep form (RFC 4013) as of Unicode 3.2, in UTF-8, which revisions 5 and 6 take (ISO 32000-2, 7.6.4.3.3), where that isn't the text as typed (`Saslprep`); its SASLprep form by a later Unicode, where that's another again, as writers whose SASLprep normalizes by a later Unicode set it (`SaslprepCurrentUnicode`); in UTF-8, as typed, as writers that skip SASLprep set it; then, for revisions 2 to 4, the text composed (NFC, so an accent typed apart from its letter has a byte) in PDFDocEncoding, WinAnsiEncoding and MacRomanEncoding (Annex D), each where every character has a byte, as qpdf tries them; none twice among those a revision takes first. A password SASLprep refuses has the rest alone. `Encoded::verbatim` takes bytes as they are. An `Encoded` is wiped when it's dropped, and neither its `Debug` nor a `Password`'s says the password. `Encoding::fits` says which revisions an encoding's passwords can have been set for: SASLprep's two 5 and 6, the single-byte ones 2 to 4, UTF-8 and bytes as given any. Composing the text first never takes from a password a single-byte form it had as typed: a test holds each character of the three tables to being its own NFC, alone and beside any other of theirs.
- **A new file's password, strictly.** `Password::prepared` gives its SASLprep form, tagged `Encoding::Saslprep`, of 1 to 127 bytes; or `Unusable`, `#[non_exhaustive]`, saying why it can't be one: `Prohibited`, a character SASLprep doesn't allow, the first of the typed text's that it refuses whatever is around it (stringprep's error says no character but of the text it made), one Unicode 3.2 hadn't assigned among them, though a later Unicode decomposes it into ones it had; `Bidi`, right-to-left text it doesn't allow; `TooLong`, over 127 bytes, which a reader would cut; `Vanished`, a password that prepares to nothing; `Empty`; `Unprepared`, bytes not as `prepared` gives them, for a new file's password given in another encoding; and `Ambiguous`, a password whose SASLprep forms by Unicode 3.2 and by a later Unicode differ, named at the character where they part, which readers would prepare apart. `Prohibited` and `Ambiguous` carry that character of the password, which `Display` writes as its code point and `Debug` as itself, so a caller that logs one logs that much of the password; their docs say so. A program that prepares its user's new password names it to them, which is what it's for.
- **A new file's encryption.** `Handler::create` makes a revision 6 encryption dictionary (`/V 5 /R 6`, AES-256 by the crypt filter `/StdCF`, `/CFM /AESV3`), by Algorithms 8, 9 and 10, and the handler that encrypts under it, protected as a `Protection` says: the user's password (a security dialog's open password), the owner's (its permissions password) or both, each prepared; the permissions, what one who opens the file by the user's password may do; and `/EncryptMetadata`. Both: each opens the file, the user's under the permissions, the owner's with every one. The user's alone: the owner's is the user's, so the one password opens the file as the owner's. The owner's alone: the user's is the empty password, so anyone opens the file, under the permissions, and the owner's lifts them, a file that limits what's done with it rather than who reads it. `/P` is the permissions as `Permissions::p` writes them, bit 10 set whatever's asked, as PDF 2.0 has a writer set it (Table 22), every permission `/P -4`; `/Perms` confirms it. The handler is the owner's, `opened_by` none, its `permissions` those written. Refused, nothing drawn (`Unusable`), for the first of these: the user's password, then the owner's, where given, not in SASLprep's form (`Unprepared`), or SASLprep's form that's empty (`Empty`) or over 127 bytes (`TooLong`), or that isn't a password prepared itself (`Unprepared`), as `encodings` may give each: 3.2's form of a password whose later Unicode's form is another is taken only where it prepares to itself; neither given (`Empty`), as a file anyone opens with every permission isn't protected; and permissions withheld where the owner's password is the user's, none given apart or the same bytes (`Shared`), as whoever opens the file would open it as its owner, whom they don't bind (bit 10, put back, isn't withheld). `Protection` is `#[non_exhaustive]`, made by `Protection::new` (one password, the user's and the owner's, every permission, the metadata encrypted) or from `Protection::DEFAULT` or `default()` (no password, every permission, the metadata encrypted), its fields set after; its `Debug` gives each password's encoding, not its bytes, and it has no `PartialEq` or `Hash`, as it holds passwords. The file's key, the user's validation and key salts, the owner's, and `/Perms`' random bytes are drawn in that order, whichever passwords are given, from a random number generator the caller passes, rand_core's `CryptoRng`, behind `dyn CryptoRng` or not, so that pdf-crypt has no randomness of its own and a seeded generator gives the same dictionary each time. The dictionary is whole as it's given: a crypt filter's `/AuthEvent` and `/Length`, which `CryptFilter` has no fields for, are the writer's to write or leave out.
- **Permissions.** `Permissions` is a set of the eight permissions `/P` has a bit for (ISO 32000-2, 7.6.4.2, Table 22), each a constant: `PRINT`, `MODIFY`, `COPY`, `ANNOTATE`, `FILL_FORMS`, `ACCESSIBILITY`, `ASSEMBLE` and `PRINT_HIGH`, with `NONE` and `ALL`; joined by `|` or `union`, read by `contains`, taken from by `without`. `Permissions::p` writes a set as `/P`, as a file of revision 3 or later has it: bits 1 and 2 clear, 7, 8 and 13 to 32 set, so negative, every permission -4. `Permissions::from_p` reads `/P`'s low 32 bits by a revision's meaning of them: from revision 3 each of the eight as written; at revision 2, which has four of them, each of the other four following the bit that covers it there (filling in forms annotating, accessibility copying, assembling modifying, printing at high resolution printing); every other bit ignored, as a reader ignores it, and as qpdf reads them. `Handler::permissions` says what a file's `/P` grants one who opens it by the user's password, read so: a handler opened by the owner's password says them too, and a created one what it wrote; `/P`'s, not `/Perms`' copy, where the two disagree, as qpdf reads them, `Fault::Perms` saying they do. `Handler`'s `Debug` says them. A security dialog's levels are reachable from a set: `Printing` (`Denied`, `Low`, `High`) and `Changes` (`Denied`, `Assemble`, `FillForms`, `CommentAndFill`, `Any`), each made a set by `Permissions::from`, each level of changes granting the one before it and more, as qpdf 12.4.2's `--modify` levels set the bits; `Permissions::printing` reads printing's level back, and none is read back for changes, as a file's bits needn't be one of the five. `ANNOTATE` grants filling in forms too, whatever `FILL_FORMS` says, as bit 6 does, and both docs say so. A `Permissions`' `Debug` names the bits, `Permissions(PRINT | COPY)`, `Permissions(NONE)`, and its `Display` says them in words, `print, copy`, `none`. They're said, not enforced: honouring them is a reader's, as one who can open a file can decrypt all of it, whatever they withhold.
- **rand_core re-exported** (`pdf_crypt::rand_core`), 0.10, the version RustCrypto's crates under it take, so that a caller names the `CryptoRng` `create` takes without a dependency of its own. It has no dependencies, and builds with Rust 1.89.
- **Encrypting for a writer.** `Handler::encrypt_string` and `encrypt_stream` encrypt as `decrypt_string` and `decrypt_stream` decrypt: by the crypt filter strings or streams are encrypted with, or a stream's own (`named`'s method). AES's IV is the first 16 bytes of HMAC-SHA256 (RustCrypto's `hmac`), under the file's key, of a context's length (8 bytes, big-endian), the context, which is the caller's name for the object, and the data: deterministic, so the same object encrypts to the same bytes on every save, and no IV serves two plaintexts. RC4 takes no IV, `/Identity` and `/None` leave the data as it is, and a method that isn't one is refused (`Fault::Method`). The MAC is keyed once, when the handler opens; `Handler` is `Clone`, `Send` and `Sync`, and its `Debug` leaves the MAC out with the key. Under RC4, which takes no IV, an object written again at its number and generation with a string or stream changed, as an incremental update writes it, XORs with its earlier version to the XOR of the two plaintexts, and so does an object a whole save or an update puts at a number another object had, as a writer that renumbers does: what leaks, when, and what a writer does instead (a whole file under a new AES-256 encryption, `create`) is said in `Method::Rc4`'s docs and the README. `Method::Rc4` says what that comes to for a writer that renumbers, and for a file laid out under Annex F, whose objects all move: every number's keystream encrypts another object's plaintext.
- **Keys kept in, and wiped.** Neither the file's key nor an object's is public, and `Handler`'s `Debug` leaves the key out. The file's key, each object's, and every buffer a password's or a key's bytes pass through on the way to one (the padded password, the MD5 and SHA-2 inputs built from it, the intermediate keys and digests, RC4's round keys, revision 6's rounds) are held in `zeroize`'s `Zeroizing`, sized where they're made, and wiped when dropped. AES keeps a key's schedule in place of the key, made once a key, and a handler of `/V` 5, whose AES strings and streams are all under the file's key, keys it once, when it opens. RustCrypto's `aes`, `cbc`, `md-5`, `rc4`, `sha2` and `hmac` are built with their `zeroize` features, which wipe their key schedules and hashing state. What it can't reach, the README says.
- **An error's `Debug` without what decrypted.** `Error`'s `Debug` gives the length of its `data`, not its bytes, which are a string's or a stream's plaintext: `Error { data: Some(23 bytes), fault: Padding }`, so a log, a failed assertion or `unwrap` never prints it. The field is public, for a caller that wants the bytes. Two errors whose data are the same length have the same `Debug`, whatever their bytes, so a test compares errors by `==`, never by their `Debug` text, and takes `data` itself where it wants the bytes.
- **A writer for tests** (the `writer` feature, off by default; docs.rs documents the crate without it): an encryption dictionary for a user's and an owner's password of each kind (Algorithms 3, 4, 5, 8, 9, 10; revisions 5 and 6 by the code `create` uses), and strings and streams encrypted, with salts, keys and IVs given. Its encryptors refuse a crypt filter the dictionary hasn't, or whose method isn't one (`Fault::Method`), as the public ones and decrypting do. `writer::Kind` is `#[non_exhaustive]`, as kinds can come, and `Hash`; `writer::Settings`' `Debug` leaves both passwords out, the rest, its `/ID` among it, as given.
- **Rust 1.89**, the family's minimum, which RustCrypto's current releases need: the next entry says what each brings.
- **Primitives.** RustCrypto's: MD5 (`md-5`), SHA-256, SHA-384 and SHA-512 (`sha2`), HMAC-SHA256 (`hmac`), RC4 (`rc4`), and AES-128 and AES-256 (`aes`, in CBC by `cbc`). The lock holds `aes` 0.9.4 (Rust 1.89: VAES on x86 by default and a smaller key schedule in software), `sha2` 0.11.1 (Rust 1.88: a soundness fix in its AArch64 backends' `unsafe` code, which loaded their round constants through a reference to one word, against Rust's aliasing model (Stacked Borrows), reached on an AArch64 CPU with the SHA-2 instructions, with no miscompilation reported) and, under `hmac` 0.13's `digest` `mac`, `ctutils` 0.4.8 with `cmov` (Rust 1.87: fixes to constant-time code, its masks and comparisons, on none of this crate's paths, as it compares no MAC: HMAC-SHA256's output is an IV here, never checked). The requirements (`0.9`, `0.11`, digest's) admit each one's line, which a project takes by `cargo update`; Cargo's resolver, when it minds Rust versions (resolver 3, edition 2024's), picks what the project's Rust builds.
- **SASLprep by `stringprep`** 0.1.5, with `unicode-normalization` 0.1 (the tables it composes the single-byte forms' text by), which bring `unicode-bidi`, `unicode-properties` and `tinyvec`; each builds with Rust 1.89. `unicode-normalization` 0.1.26 is `(MIT OR Apache-2.0) AND Unicode-3.0`, for Unicode's tables, a permissive licence. Its normalization is by the Unicode `unicode-normalization` has, and its form is taken back to 3.2's, which SASLprep is of (RFC 3454), as UAX #15 has it done (section 11.3): Corrigendum #4's five characters (U+2F868, U+2F874, U+2F91F, U+2F95F, U+2F9BF) mapped first to the decompositions 3.2 gave them, a character 3.2 hadn't assigned refused, and the text composed by UAX #15 3.2.0's definition of a blocked character, which Corrigendum #5 changed. That table and that rule are this crate's; a test holds the composites the rule makes to UAX #15's Table 10, each a letter or vowel sign SASLprep allows.
- **Exhaustive on purpose, or not, and said.** `Error`, `Password` and `writer::Settings` are exhaustive, each doc saying why: each is built by a literal and taken apart by its public fields (an error is what decrypted and why, a password its text, the writer's settings what a test writes a file with), so a field more would be a breaking release. `Printing` and `Changes` are too, a security dialog's designed levels, each listed whole in its `ALL`, in the order of their discriminants, so a level more would be a breaking release. `Dictionary`, `CryptFilter`, `Protection`, `Method`, `Refused`, `Fault`, `Encoding`, `Unusable` and `writer::Kind` are `#[non_exhaustive]`, so a field, a method, a refusal, a fault, an encoding, a reason or a kind can join one in a minor release (a new file's choice joining `Protection`, a revision ISO/TS 32003 adds, say), a match on it needing a wildcard; `Method`'s doc names the method that may: ISO/TS 32003's AES-GCM (`/AESV4`), whose dictionaries (`/V 6 /R 7`) are refused as `Refused::Version` until it's read. `Refused::OtherHandler` and `Refused::Version` are too, matched with `..`, so a field can come; `Fault`'s variants aren't, each field the whole of what it says (a length, a count, a name), so one is built by a literal, as a test compares with it, and a fault that says more joins as a variant of its own. `Permissions` keeps its bits to itself, as `Handler` and `Encoded` keep their fields.
- **Errors, and hashing.** `Refused`, `Fault`, `Unusable` and `Error` derive `Display` and `std::error::Error` with thiserror, none with a `source`; `Error` says its fault's text. `Dictionary`, `CryptFilter`, `Method`, `Fault`, `Refused`, `Encoding`, `Unusable`, `Permissions`, `Printing`, `Changes` and `writer::Kind` are `Hash`, so a caller can key a map by one; `Error`, `Encoded`, `Password`, `Protection`, `Handler` and `writer::Settings` aren't, as each holds plaintext, a whole password or a key. `Unusable` is, though `Prohibited` and `Ambiguous` carry one character of the password, which its `Display` and `Debug` give anyway; `Shared` carries nothing of either password.
- **Marked, and `const` where it can be.** `#[must_use]` is on every function whose result dropped is a mistake and whose type doesn't say so itself: `Handler::opened_by`, `owner`, `strings`, `streams`, `encrypts_metadata`, `permissions`, `faults` and `named`; `Encoding::fits`; `Encoded::verbatim`, `encoding` and `as_bytes`; `Password::encodings`; `Permissions::from_p`, `p`, `contains`, `union`, `without` and `printing`; `Protection::new`; and `writer::dictionary`. None is on what gives a `Result`. `Handler::opened_by`, `owner`, `strings`, `streams`, `encrypts_metadata` and `permissions`, `Encoded::encoding`, `Encoding::fits`, those six of `Permissions` and `Protection::new` are `const fn`s, so whether an encoding fits a revision, or a set's `/P`, can be had in a constant. Every function that gives a `Result` says what fails it and when, under `# Errors`: `Handler::open`, `create`, `decrypt_string`, `decrypt_stream`, `encrypt_string` and `encrypt_stream`, `Password::prepared`, and the writer's `encrypt_string` and `encrypt_stream`.
- **Benchmarks.** `cargo bench -p pdf-crypt --features writer` times opening a file by a password, a new file's dictionary, a password's forms, and decrypting and encrypting strings and streams, on inputs the benchmarks make as they run, the same on every run: `Handler::open` of the writer's dictionary of each kind by the user's password, which is tried as the owner's first, and by the owner's, and of revision 6's by a wrong one, hashed both ways; `Handler::create` from a generator seeded afresh each time; `Password::encodings` and `prepared` of ASCII, Latin text typed composed and decomposed, and Japanese with full-width digits; 10,000 strings of 8 to 64 bytes over 2,000 objects, decrypted under RC4 of 40 and 128 bits, AES-128 and AES-256, and encrypted under RC4 of 128 bits and both AESs; and a page's content, 1 MiB, as 256 streams of 4 KiB and as one, decrypted under RC4, AES-128 and AES-256, and as one encrypted under both AESs. Each input is held to what it gives before it's timed: a handler to opening as the owner's or the user's, a new file's dictionary to opening by its password, a password to its forms, each string and stream to decrypting to its plaintext. Throughput is in bytes of plaintext for decrypting and encrypting, and in calls for the rest. They need the `writer` feature, whose dictionaries they open; without it, cargo skips them. So a change is judged before and after it. The harness is criterion, a dev-dependency never built for a user of the crate, and `benches/` is outside the package.
- **The package, checked before a publish.** CI packages the crate as a publish would (`cargo publish --dry-run`, in a target directory of its own made fresh each time, so a stale build can't pass or fail it) and checks what the package holds: `src/`, the README, the CHANGELOG, the manifest and the lock, nothing else, no benchmark among them. CI tests the crate on Rust 1.89, its `rust-version`, without the `writer` feature, the build a dependent gets, and lints its library without it too; the README's first example, which needs no feature, runs there as the crate doc's, a test holding the two alike line for line. The manifest names the crate's documentation (docs.rs). The README's licence links are the repository's URLs, which reach the files from crates.io and docs.rs, and a test holds them so.
- **Where it comes from.** Written for pdf-lint, a PDF checker, whose reader opens an encrypted file by a password through it, and for a writer; no release before this one had it, pdf-lint 0.1.0's included. A password's UTF-8 and single-byte forms and their three tables were first written in pdf-lint, after 0.1.0 and in no release, and moved here: every form they gave there, `encodings` gives, in the same order, after SASLprep's.
- **Tests.** Each kind qpdf writes, opened by either password with qpdf's own key, its strings decrypted; the writer's, each way; each fault and refusal; RFC 4013's SASLprep examples, the characters and sequences Unicode's Corrigenda #4 and #5 changed, read and refused, and revision 6 dictionaries set with either form, each opened by the one set; RFC 4231's HMAC-SHA256 cases; a new file's dictionary opened by its password both ways, drawn in order, its bytes as an implementation of the algorithms apart gives them for a seeded generator's draws; a new file under each combination of passwords opened by each, by the empty one and by a wrong one, as the owner's or the user's as its protection says, its `/P` and `/Perms` read back, each refusal with nothing drawn, and a dictionary with an owner's password apart drawn as the one password's, its `/O`, `/OE` and `/Perms` as that implementation gives them; `/P` read at revisions 0 to 7, edge values and every set of the eight written and read back; the levels of printing and changes as qpdf sets their bits; a set's `Debug` and `Display`; a `Protection`'s `Debug` without either password; which revisions each encoding fits, 0 to 8 and far from them, each answer written out; and a fuzz target, `just fuzz crypt`, on dictionaries of any fields and on the writer's that open, now and then another handler's or one without a `/Filter`, on new files' dictionaries for any passwords, the user's, the owner's, both or neither, and any permissions, each opened by each password and its permissions read back, and on a password's forms and prepared form for any text, whose bodies three unit tests run. The target holds a dictionary refused as another handler's, by its name, exactly where its `/Filter` names one that isn't `/Standard`; a version refused as the dictionary's `/V` and `/R`; a method that isn't one, among those it decrypts and encrypts by, refused alike both ways; and every decrypt error's `Debug` giving what decrypted by its length, never its bytes.
