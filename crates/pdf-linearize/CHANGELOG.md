# Changelog

## 0.1.0 (unreleased)

- **The plan.** `plan::plan` (ISO 32000-2, F.3) takes a `Graph`, built up by `Graph::new(catalog, kind)` and its methods, one flat list of references and a range of it per object: `object` and each `Node`'s `packable` and `late`, `page` with a `Page` (`#[non_exhaustive]`, by `Page::new`, its `contents` and `thumb`), `first_page`, `tree_node`, `open`, `group` with a `Group` (`#[non_exhaustive]`) and `outlines_first`. It gives a `Plan`: `writes`, what a caller serializes in file order, each a `Write` (`What`, its number, its `Part`); `containers`, each object stream's number and members; `number`; `used`; `part_writes`, `page_writes`, `thumb_writes`, `group_writes`; `entries`, the shared object table's; `shared`, `group_shared`; `first_page`, `first_page_number`, `dictionary_number`, `first_xref_number`, `main_xref_number`, `hint_number`, `size`; and `shared_entries`, `shared_visits`, what its lists cost. `Kind` says what lists the file, a table or a stream, which decides the layout's own numbers and whether anything can be packed.
- **What the tables want of a plan.** `Plan::page_contents`, a page's streams in its section, from `Page::contents`; `thumb_shared_writes`, what several thumbnails reach, after the last of them, each thumbnail's own sealed apart so a table can name it; `files`, a `FileGroup` per root of `Group::EmbeddedFile`, its own number and writes, sealed apart, and `file_shared`, what each refers to; `catalog_number`.
- **The parts.** Part 4: the catalog, then what's at open, not gone into (F.3.5). Part 6: the first page's object and all its walk went into, in the walk's order, what's `late` last, whatever a later page reaches of it, then the outlines under `outlines_first` (F.3.7, F.4.3). Part 7: each other page in page order, skipping the first (F.3.8), its object first, what it alone uses, `late` last. Part 8: what several later pages reach, by number. Part 9: the tree's nodes, thumbnails by page, page 0's first (F.3.10), each group in `Group`'s order, what's left by number. An object placed once stays there. A page given as a tree node or at open stays a page.
- **The numbers (F.3.1, F.3.6).** From 1, parts 7, 8 and 9's writes in file order, the main cross-reference stream under `Kind::Stream`, then their object streams' members; then the dictionary, the first-page cross-reference stream, parts 4 and 6's writes in file order, their members, and the hint stream last. All at generation 0.
- **Which pages use an object.** `plan::Use`, as `Plan::used` gives it, from a walk from the first page and then the others in order (`page_uses`, private for now): each object entered at most twice, on its own stack, stopped at pages and tree nodes but the page walked from, the catalog, and what's at open.
- **Object streams.** `plan::group`, a pure function of each object's number and its `Use`, with `MEMBERS`, the most a stream holds, 100. A plan calls it once per region: part 4's, the first page's, the outlines' under `outlines_first`, parts 7 and 8's by their uses, the tree's nodes', thumbnails', each group's with a table, and `Group::Other` with what no group reached. A stream of one later page's members stays in that page's section; one with several pages' or shared members is part 8's, one entry of the shared table. The catalog and page objects are never packed, whatever `Node::packable` says (F.3.1).
- **The shared lists (F.4.2, F.4.3).** `Plan::entries`: in part 6, each stretch no later page reaches is one entry and each write one reaches another; in part 8, each write is one. `Plan::shared`: for each later page, the entries of all it reaches, a member by its object stream (F.3.1), each once, in order, by a walk of its own that stops where the first did; none for the first page. `Plan::group_shared`: the same for `Group::Form`, `Structure` and `Renditions`, whose tables list them (F.4.6); `Plan::file_shared`, each embedded file's (F.4.7).
- **The hint tables (F.4), `hint`, both ways.** `PageOffsets`, `SharedObjects`, `Generic`, `Extended`, `Thumbnails`, `EmbeddedFiles`, each `write` and `read`, no bit reader's type in their API; `HintKeys`, and `tables` for all a stream's dictionary says it has; `position` and `located`, where a thing reads in a table, as if the hint stream weren't there (F.4.1). Each item's run across entries ends on a byte boundary, which F.4.1 doesn't say and qpdf, PDFium and real files all do. A table's constructor (`of`) gives a header as narrow as readers take: a bit at least where PDFium's reader refuses a width of 0, content lengths as wide as page lengths as it reads them. Reading: a field past the data is `hint::Error::PastEnd` at its bit; a width past 32 is `Width`; a key past the data `TableAt`; a count that wants more bits than there are is refused before there's room made for it; and pages against `Limits::pages`, entries against `Limits::hint_entries`, new, 2^24, all a stream's tables together, as a width of 0 reads no bits. `Limits` is `#[non_exhaustive]` still, so its new field breaks nothing.
- **The bytes around the bodies, `assemble`.** `layout::assemble(plan, lengths, options, encode)`: lengths of the caller's bodies, one per write; `layout::Options` (`new`, `version`, `trailer`); a closure from `Stream` (`what`, a `StreamKind`, `number`, `data`, `columns`) to `Encoded` (`new`, `plain`). It gives a `Layout`: `pieces`, each a `Piece` (`Bytes` or `Body`), `len`, `position`, `first_page_end`, `hint_extent`, `first_section`, `main_section`, `hint_data`, `hint_keys`. In order: the header and a binary comment, the dictionary, the first-page section, part 4, the hint stream, parts 6 to 9, the main section. The dictionary's padded to a fixed 200 bytes after its `endobj`, and written last. A table's `/Prev` has room for any position, so its length is known first, and it's one pass. A stream section (`/W [1 4 2]`) is given room from what a first guess at its rows comes to, and goes round where what it filters to doesn't fit, the room only growing, padded with spaces after its `endobj` when it does. `/T` is the line's end before a main table's first row, or the main stream's object (Table F.1). Refused, by a `layout::Error<E>`: not one length a write, a file past 2^32 bytes, a closure's refusal (`Encode`), and a closure that's longer each round (`Unsettled`).
- **What's written in the tables.** Which are written follows the groups a graph was given, each even with nothing left to it (F.3.6); thumbnails where one exists; no page label table. Entries are in the order of the pages' numbers, whichever is the first page, as PDFium and qpdf read them. The first page's counts all of part 6 and names no shared object (F.4.2). A page's content items are its own streams', from the first to the last's end, and 0 where it has none in its section. Numerators take no bits, over a denominator of 4. Part 8's number and place are said even when it's empty, where it would be, as PDFium's reader refuses a 0. Each embedded file is a group of its own, one with shared objects a group of no objects beside it (F.4.7), and their identifiers are in the page offset table's width, its width grown to cover them. Nothing's hashed: no signature's written, and one read is kept as it was.
- **The family adapter, `family`, a default feature.** `family::linearize(out, doc, encryptor, from, options)` and `linearize_bytes(bytes, passwords, options)`, with `Options` (`kind`, `pack`, `deflate`, `threads`, `version`, `first_page`, `limits`, `stop`), `FirstPage` (`OpenAction`, `Index`), `Linearized` (`id`, `layout`), `Error` and `PageTree`. It takes pdf-structure, pdf-objects and pdf-semantics, without its clock; the engine builds and tests without it. What's written: every object the trailer reaches at the plan's number, copied through `write::Parts` where the rules for a copy hold; object streams built on threads, one too big for the reader planned again without its members; inheritable attributes pushed down to each page as written, a page that needs nothing still copied, and taken off every node; the catalog's `/ViewerPreferences`, `/PageMode`, `/OpenAction`, `/AcroForm` (alone) and `/Threads` with its threads in part 4 (F.3.5); `/DPartRoot`'s nodes and any page or node the tree doesn't list as stops (F.3.7), a page never packed; part 9's groups, the outline in the order a viewer shows it and what's under a closed item after (F.3.10), and in part 6 under `/PageMode /UseOutlines`; images and font files last in a page's section; the first page where `/OpenAction` opens, named destinations too (F.3.7). The header is the document's, at least 1.5 under a stream. The `/ID`'s first string is kept, the second XXH3-128 of the bodies. An object only a stream's `/Length` names isn't written, as `/Length` is written direct, nor a null object. Each refusal leaves `out` as it was given.
- **Encrypted files, through the family adapter.** `family::linearize` under an `Encryptor`, `Encryptor::of` a reading or `Encryptor::create`, by `Encryptor::renumbered`, `whole` and `encrypting_renumbered`; `linearize_bytes` opens a file by its passwords and keeps its encryption. Every string and stream is encrypted under the number it's written at, the hint stream's data too (7.6), a cross-reference stream not (7.5.8.2). The encryption dictionary and what its values refer to go in part 4 (F.3.5), in the clear (7.6.2), written from the encryptor, what the file read named left out: a new file's, which has no number, is given the graph a number past every object's and every reference's. `/Encrypt` in the trailer stays there. `/ID`'s first string is the encryptor's, else the document's. An object as read is copied at its new number only where no key is made from the number (AES-256), a metadata stream under `/EncryptMetadata false` left in the clear at its new number. Asked to pack under an encryption that doesn't, `Encryptor::packs`, the file is written unpacked. With no encryptor an encrypted reading is written in the clear, as `write::document` does. `Error::Locked` for a document no password opened, whichever. **Every number is reused under keys made per object:** a section of this layout lists none free but 0 (F.3.4, F.3.11), so under RC4 each number's keystream encrypts another object's plaintext, as the module's doc and pdf-crypt's `Method::Rc4` say; `Encryptor::create` is the way out.
- **What a tree must give a page.** `PageTree`: a place with no page at it, a page written in place or listed before, ISO's rules and PDFium's listing other pages, or reading an inheritable attribute differently, and a node in place holding one.
- **Tests of what the adapter writes.** `tests/family.rs`, each promise above read back with pdf-structure's reader; `tests/qpdf.rs`, both of qpdf's checks on each kind, each warning a class with its reason; `fuzz::over`, any bytes as a file, laid out in each kind and read back, every object the same under the numbering. `tests/pdfium`, small linearized files and broken ones from a Python layout of its own, each given to PDFium as its availability API asks (the `avail` kind of the repository's oracle), held at the pin by `just test-pdfium`.
- **The check.** `check::check(facts, limits, sink)` (at the root too), the facts of a file as written against each other. `Facts` (`Facts::new`, `#[non_exhaustive]`, its fields public to set): `len`, `header`, `first_object` (`FirstObject::new`, its keys as `Raw`), `first` and `main` (`SectionFacts::new`, each section's `subsections`, `rows` in the order written, each `RowFacts::new` of a `RowEntry`, `first_row`, `stream`, `size`, `prev`, `root`, `startxref`, `hybrid`), `update`, `hint` (`HintFacts::new`, its `keys`, `overflow`, `HintData`), `pages` (`PageFacts::new`), `nodes` (an `Attribute` each), `objects` (`Extent::new`), `graph`. `Verdict`: `linearized`, qpdf's test, the first object starting within 1024 bytes of the header, a dictionary, its `/Linearized`'s integer part 1, its `/L` the length from the header; `holds`; `hints_read`. `Finding` (`#[non_exhaustive]`, `Copy`, its `Display` the whole message, its clause and its place), its `grade()` a `Grade`, `Error` or `Departure`. `Sink` as pdf-semantics' is: `finding`, `wants`; `()`, `&mut S`, `Vec<Finding>`. A sink that doesn't want findings is told none, and looking stops at the first error, as nothing can change the `Verdict` by then, which is the same whatever the sink. Told, by clause: Table F.1, a value of the wrong type or by reference, `/L`, `/O`, `/N`, `/E`, `/T`, `/H`'s place and length; F.3.3, a dictionary running past the first 1024 bytes; F.3.4, the first section's shape and `/Size`; F.3.11, the main section's and `startxref`; F.3.1, what's packed that can't be, generations, the groups' numbers, what's above what's packed, what's written out of number order; F.3.6, the hint stream not last, its keys, its tables overrunning; F.3.7, F.3.10, what a page or a node holds; F.4.2 to F.4.7, every table's positions, counts, lengths and identifiers against where the sections have things, as a reader adding them up finds them. Where the graph's given (`plan` on it, in the file's numbers), what each page reaches to its section and its list. Which `Finding` is a `Departure` is set by what real files have; a position, a length, a count or an identifier past its table is an `Error` by definition.
- **The check of a reading, `family`.** `family::facts(reading, limits)`, what a `pdf_structure::Reading` says of a file, `family::check(reading, limits, sink)`, those judged. A file that doesn't say it's linearized, or whose `/L` isn't its length, has no more read than it takes to say so; the rest takes each section's rows (`Reading::sections`), its first object (`Reading::first_object`), the hint stream's data, decrypted by the reading's key, the page tree by ISO's rules and a whole read for the graph. No key for the data says nothing of it, and `hints_read` false.
- **What a check wants of a layout.** `Layout::main_first_entry`, the dictionary's `/T`.
- **Tests of the check.** Each finding from a plan's facts with one thing changed; `tests/facts.rs`, facts built from outside the crate with no family type, by a caller's way in; `tests/check.rs`, what the writer writes, under each key too, and bytes changed since; `tests/pdfium.rs`, `check` held to PDFium's answers on the tracked cases, `differ.tsv` naming what's chosen. A fuzz body, `fuzz::facts`, any facts judged alike whatever the sink; `fuzz::graphs` holds what's assembled clean, `fuzz::over` what's written. The tracked cases' first shared entry now counts the three objects it spans, which PDFium doesn't read, its answers recorded again the same but where a table is a byte longer.
- **Refusals and caps.** `plan::Error` (`#[non_exhaustive]`, thiserror): no pages, a page or the catalog not among the objects, the catalog given as a page, an object or a page given twice, a first page past the pages, a packable object under `Kind::Table`, and past `Limits` (`#[non_exhaustive]`, `Limits::DEFAULT`): `objects`, every number a file uses, what's packed and the layout's own among them, 8,388,606; `pages`, 1,048,574; and the lists' `shared_entries`, 2^24, and `shared_visits`, 2^28.
- **Tests.** `tests/engine.rs`, an outside crate writing small files from hand-written bodies with no adapter, read back from their bytes with a few lines of its own: two pages, shared and not, a first page other than page 0, a form's and an outline's groups, thumbnails, every other table, many pages, table and stream kinds, packed, and every promise above on each. `tests/qpdf.rs`, each of those files' whole answer from `qpdf --check-linearization`, under `just test-qpdf`, each warning explained: the hint stream numbered last, a form's fields not in part 4, a first page other than 0. Each table against bits laid out by hand. Unit tests for each part's order, the numbers of each group and kind, the first page's objects under another first page, the walk's stops, late objects and outlines, part 9's order, each region's object streams, a stream of two pages, each shared list, each refusal and each cap at its edge. The walk's two tests and the grouping's come with them.
- **A fuzz body and target** (`just fuzz linearize`): any bytes as a graph, refused for what it has or planned, each object once, the numbers a bijection onto 1..size in the order above, each page first in its section, each `Use`, each part and each shared list what a plain walk of the graph gives, each cap at its edge giving the same plan or a refusal. Then `assemble`: with its streams as they are, with a first-page stream wanting more room, which settles, and with one that always does, refused: its positions what its pieces add up to, its tables read back what the plan says. And the same bytes as a hint stream, at any positions under small caps: an error, or tables that write and read the same. A stable unit test (`fuzz_bodies_run`) runs them.
