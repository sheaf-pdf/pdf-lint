# pdf-content-streams

PDF content streams (ISO 32000-2, §7.8.2), read as PDFium reads them, as of chromium/8125, a development snapshot of PDFium that the crate's tests hold it to, in a small Rust crate on [pdf-tokenizer](https://crates.io/crates/pdf-tokenizer), whose tokens it reads by PDFium's rules, [pdf-objects](https://crates.io/crates/pdf-objects), which it re-exports so its values are named at the version it's built with, [pdf-color](https://crates.io/crates/pdf-color), re-exported too, which counts a color space's components as PDFium does, and [pdf-filters](https://crates.io/crates/pdf-filters), whose Flate and LZW decoders find where an inline image's data ends as PDFium's do, Flate on [zlib-rs](https://crates.io/crates/zlib-rs): each token with where it is and its bytes as written, an inline image's data found by PDFium's rules, each operation with its operands held in the item, operands read as values only when asked, as PDFium reads them, a page's streams joined as one, every place in them mapped back to the stream it's in, each operator typed by ISO 32000-2's Annex A, with the operands it takes and where it may be used, and a page's `q`/`Q` balance, its marked content and the resource names it uses; and content written, each operator and its operands the same way every time, the resources it draws with named at the end by a digest of what they are, or spliced, ranges of it taken out and every other byte kept, only where that can't change what's drawn after them.

It's made for what reads content to draw it, check it or edit it, and what writes it. A token is a range of the bytes read, so what it says can point at them; an operation of sixteen operands or fewer allocates nothing; nothing is read that isn't asked for; and no file is read here: the caller gives the streams, decoded, what an inline image's size depends on, which `ResCx::read` reads from a resources dictionary through the caller's resolver, the property lists marked content names, and, for the names the writer gives, the resources dictionary its content goes with, read through that resolver too.

## What it does

- **Tokens.** `tokens` gives a stream's tokens in order, each with its range: an operator, any word that isn't a number, `true`, `false` or `null`; an operand as written, a number, a name, a string, an array or a dictionary, as far as PDFium reads it, or a closing delimiter with nothing to close, which PDFium passes over; and an inline image, `BI` to `EI`, one token, with where its data is, but for a `BI` with a keyword where its dictionary's key should be, which PDFium reads as no image, and which is an operator of its own here. Between them is only white-space and comments. Tokens end where PDFium's `CPDF_StreamParser` ends them, pdf-tokenizer's read by PDFium's rules: at white-space, 0x80 and 0xFF among it beside ISO 32000-2's six bytes, and delimiters; a word of digits, signs and points is a number, and strings nest. An array or a dictionary ends where PDFium's `ReadNextObject` ends it: an array at the first `]` read for an element, as an array inside an array, outside any dictionary, opens none, so `[[1] 2]` is `[[1]`, then `2` and `]`; a dictionary at its `>>`, or, none, at a key that's no name, a string's `(` or a hex string's `<` alone, or at a value that's no object, so `<< 1 2 >>` is `<< 1`, and in an array, the array then reads on; and inside a dictionary, arrays nest. What's after one is read on, as content. What an operator does is no part of it, so one nobody knows is a token like any other.
- **Inline images, as PDFium finds their data** (`ReadInlineStream`): an unfiltered image by its exact size, from `/W`, `/H`, `/BPC` and its color space's components (below), each number as PDFium reads an integer from it (a real cut to its whole part, `true` 1, what's no number 0), held in 32 bits; `/AHx`, `/A85` and `/RL` to their ends as PDFium's decoders find them; then on to the next `EI`, its tokens read as PDFium reads them. A filter PDFium can't decode, one of those that finds no end, or an image no size counts reads on from its data's start to the next `EI`, and so does an image of any filter whose size overflows 32 bits as PDFium counts it, or has a negative width, which PDFium reads no data of; `/L` and `/Length` PDFium doesn't read. `/Fl` and `/LZW` data is decoded, as PDFium decodes it to find its end, to where the decoder stops reading it: Flate's to what zlib counts it read, its checksum among it, and so it's decoded on zlib-rs, LZW's to its code of 257 or its last whole code; by the first of an array of filters, with the first object of an array of `/DecodeParms`, or its one with its dictionary, each parameter as PDFium reads an integer from it, `/BPC` as `/BitsPerComponent`. Where PDFium refuses the parameters (`/Colors`, `/BitsPerComponent` or `/Columns` negative, or multiplied past 2^31 − 8) or what decoding gives (an LZW code not in the table yet, LZW data that decodes to nothing, a predictor whose rows would be no bytes, a PNG predictor on nothing), it reads on from the data's start to the next `EI`, with no stream; PDFium's LZW decoder reads on past a code not in its table but the first since a clear code, as if it were the next entry, which isn't followed. Where no `EI` comes after a filter's end, PDFium keeps no stream of the data, and reads on from its start to the next `EI`, and so does this; but an unfiltered image's counted data with no `EI` after it doesn't end. PDFium decodes the data of `/DCT` and `/CCF` to find its end too, and so does this where a reading asks for it (`Limits::coded_ends`, with the `image-ends` feature, below): every row, to where the decoder stands after the last, a JPEG from its first start of image, its end counted from there, as PDFium counts it, refused where its header doesn't read or it's narrower than `/W`, one of several scans read whole to its end of image, one of one scan to past the marker after its coded data that isn't a restart, as PDFium's JPEG decoder, libjpeg-turbo, reads them; fax data's rows by `/Rows`, or `/H`, each `/Columns` wide (1728 where it isn't written, `/W` where it's 0), by `/K`'s coding, refused where either count is none or past 65,535; the stand-in's end where the decoder can't decode what PDFium's reads on through. Otherwise, a stand-in finds the end in the data's bytes: a JPEG's past its first end of image, and fax data's, or a JPEG's with none, at the first `EI` with white-space before it and white-space, a delimiter or the end after, which agree with PDFium's decoders but where a JPEG's end of image comes before its last (a thumbnail's), the coded bytes hold such an `EI`, or PDFium refuses the data. The dictionary is read as PDFium's `Handle_BeginImage` structures it: a name and its value, and so on, to `ID`; an object that's no name where a key should be ends it, the data read from after it as from after `ID`, and a keyword there makes the `BI` no image, an operator of its own, with what's after it read as content; and a value PDFium reads as no object, a keyword (`ID` among them), a closer, a brace or a dictionary that's none, takes its key out, each value read as far as PDFium reads it, as an operand is. A key is matched as written, its `#` escapes not decoded, a value's names and strings read as PDFium reads them (a color space's name looked up so), an abbreviated name read as the full one, and of a key written both abbreviated and in full the abbreviation's value counts, unless the full name's is an abbreviated name.
- **A color space's components, as PDFium counts them.** An array in an image's dictionary is read as PDFium's parser holds it and counted by pdf-color, as `[/Pattern /DeviceRGB]` is 4 and `[/Indexed /DeviceRGB 1]`, which doesn't load, 3. A name is a device space, or what the resources give: `ResCx::read` counts each space a page's or a form's `/Resources` names, as written, through the caller's resolver, reached as PDFium reaches them, a stream's dictionary among them, through at most two references. A name whose value is a reference to nothing has no entry, so an image in it is one bit of one component, as in PDFium, an object that's damaged isn't there, and any other failure to read one is the `Err`, a typed `pdf_objects::Unreadable`. Past a cap of `Limits::color` a branch of a space doesn't load, with no error, and `ResCx::capped` names those it was met for. `ResCx::new` takes counts a caller has, and `ResCx::none` is no resources. Nothing is kept between calls: a caller reading many pages of the same resources can hold what it gives.
- **Operations.** `operations` gives a stream's operations in order, a standard iterator of `Operation`s: each operator, or inline image, with the operands before it, its tokens grouped. An operation's operands' ranges are held in the item, sixteen of them, as many as PDFium keeps, before they spill to the heap; every operand is kept, up to the cap. Operand `i` is taken from the last, as PDFium takes them (`arg`), and `operands` gives them all in order. Operands at the end, which no operator takes, are no operation. An inline image is one operation, `BI` to `EI` (`InlineImage`): where its dictionary and its data are, the value under a key, either spelling, as PDFium reads it (`entry`), the length it gives its data (`length`), and what PDFium makes of its data (`stream`): a stream of some of the content's bytes, its data and any tokens between its filter's end and `EI`; a stream of none, where an unfiltered image's size counts to 0; or none, and so no image drawn, where its data is read on to `EI`. A `BI` that begins no image is an operation of its own, with no `inline_image` and the operands before it, as PDFium clears them after it.
- **Operands read when asked, as PDFium's content parser reads them.** An `Operand` is its bytes as written and where they are, and says what kind it is from how it starts: a number, a name, a string, an array or a dictionary. `name` decodes a name's `#` escapes as PDFium does, a `#` with two bytes after it an escape whatever they are, a byte that's no hex digit read as 0, and a name longer than 255 bytes as its first 255, borrowing it when there's no `#`. `number` reads a number as PDFium does, an `f32`: a word of digits, signs and points by its first 255 bytes, a whole number in 32 bits, unsigned without a sign and signed with one, 0 past them, a real the decimal it starts with, and 0 for what isn't a number word, so `--5` is 0 and `1.2.3` 1.2; an array's elements read alike. `object` reads any operand as a pdf-objects `Object`: numbers as `number` reads them, held at 64 bits as pdf-objects holds a number it reads by PDFium's rules, `--5` the integer 0 and `1.2.3` the real 1.2, names as `name` reads them, strings in their form, literal or hex, a literal string's CR or CR LF written in it kept as written and a string's first 32,767 bytes read, as PDFium reads them, and arrays and dictionaries as PDFium reads them (above), a word that's no object dropped from an array, and a dictionary with a key that's no name or a value that's no object none, a dictionary keeping every entry as pdf-objects' `Dict` does, in one pass however deep, under the caps on how deep they nest and how many values they hold. `elements` gives an array's elements as written, each where it is, gathering nothing, a `[` that opens none among them.
- **Operators.** `Operator` types each operator of ISO 32000-2's Annex A by its name, as written (`Operator::of`, `Operation::operator`), `Other` for any other word, and gives what the clause defining it says: the count and types of its operands (`Operands`, `Type`; `SC` and `sc` take a number for each component of the color space, `SCN` and `scn` the same or a pattern's name), its category of 8.2 (`Category`) and the clause. `paint` says how a painting operator paints, `F` as `f`, `clip` the rule `W` or `W*` clips by, and `builds_path` which build the path. `Operators` is a set of them, each category one. `State` says where each may be used, among the graphics objects of 8.2 (its Figure 9, with the errata: `q`, `Q` and marked content in a text object too): the content stream level, a path, a clipping path, a text object, an inline image, and the start of a Type 3 glyph description, where `d0` or `d1` comes first and nowhere else. `after` gives the state an operator leaves, where it's allowed, and `step` an operation's, an inline image `BI`, `ID` and `EI` in turn, and a `BI` that begins none the state it was in, where an image may begin. Holding content to them, an operator's operands or where it's used, is the caller's.
- **A page as one.** `Concat` joins a page's `/Contents` streams with a space between each, as PDFium joins them (one stream is borrowed as it is), and maps an offset in them back to a stream and a place in it (`Pos`, `SpanAcross`), and back again. A string or an inline image can still run from one stream into the next, as in PDFium. `Join` joins streams as they're read, under a cap (and 4 GiB, which a place in them counts to), and decodes each straight into the joined bytes when its decoder appends to a buffer, as pdf-filters' `decode_into` does: a stream past the cap, or that won't decode, is refused, the bytes cut back to where they were.
- **Balance, marked content and names.** `balance` counts a page's `q`s and `Q`s (`Balance`): the net count, and the lowest the running count goes, below 0 where a `Q` restores a state the content didn't save; ISO 32000-2 asks that they balance, a page's streams read as one (8.4.2). `marked` finds its marked content (14.6), each range a `BMC` or `BDC` opens and its `EMC` ends (`Marked`): its tag, its property list, written in the content or named and looked up in the lists the caller gives (`Properties`, its resources' `/Properties`), borrowed so ranges naming one list share it, where it is, from one stream into another, and how many ranges it's inside; an `EMC` that ends none, a range still open at the end, or ranges nested past the cap are errors. `names_used` gives the resource names content uses, by category (`ResKind`, `NameSet`): `Tf`'s font, `Do`'s external object, `gs`'s graphics state, `sh`'s shading, a color space but for the device ones, an inline image's too, by the name PDFium looks it up by, a pattern and a named property list; and `kept` what content keeps once ranges of it are taken out, its balance and names, and the names only those ranges use, the ranges in any order and overlapping, each operation found in them by one search. Each is counted an operation at a time, `Balance::take`, `MarkedNest::step`, told as each range opens and ends (`MarkedEvent`), with those still open (`open`), and `NameSet::take`, from the resource an operation names (`Operation::resource`), so a reader stepping through content for more than one finds them all in one pass.
- **Resources by what they are.** `Res` is a resource content draws with, a font, an ExtGState, a property list, an image or a form: its objects, the resource first and then those it reaches, or an object already written, by its number. It's named by what it is (`ResId`), a 128-bit digest of its objects (XXH3-128, on [twox-hash](https://crates.io/crates/twox-hash)), so that equal resources are written once and named alike: a dictionary by its keys in order, each once, a string by its bytes, whether literal or hex, a stream by its dictionary and its data, and where a value was written left out. The digest is the same on every build and platform, and isn't a security boundary.
- **Writing.** `ContentWriter` writes content, each call an operator, its operands before it, a line of its own, the same bytes for the same calls every time and on any thread: numbers (`write_number`) with at most four decimals, trailing zeros and a bare point trimmed, never an exponent or `-0`, and 0 for NaN and the infinities, but a whole number outside the signed 32-bit range keeps its point, as PDFium reads one without it as 0; strings (`write_string`) literal, `(`, `)` and `\` escaped, or in hex where a byte is a control code, so a CR, which PDFium reads in a literal string as written and ISO 32000-2 as LF, is never written raw; names as pdf-objects writes them, `#` and two hex digits for a byte that's no regular character. Text is shown as codes a font already encoded (`show`), in the font `font` names by its resource; a matrix is six numbers; and `operation` writes an operation of content read as it was, its operands and operator, an inline image whole, so content written again so reads as the same operations, but where an inline image's reading looked past its token: one PDFium keeps no stream of, the content's last where its Flate data is a header asking for a preset dictionary named past its `EI`, and, where a reading decodes them, DCT and CCITTFax data decoded past it. The resources it draws with (`Res`: a font, an ExtGState of opacity and blending, `GState`, a property list, an image or a form) are each one need in each category drawn in (`ResourceNeeds`), in the order first drawn, named only when it's finished (`finish`, `named`): `Sh` and six base32 characters of their digest, counted up past a name the resources dictionary it goes with binds to another resource (`Reserved`, read through the caller's `Resolve`, each object a name binds read once, or the names content written before was given), and the same name again where it binds the very resource, so content written again for the same resources is named alike. A name bound to an object holding a stream's data a reader placed is told by its reference alone, as a place is shared by two files laid out alike. It refuses nothing: a name PDFium would read the first 255 bytes of, or a string the first 32,767, is the caller's to keep from it.
- **Splicing.** `splice` gives a page's streams with ranges taken out, every other byte as it was, a stream nothing is taken from borrowed, and a space where the bytes kept either side would join, neither white-space by ISO 32000-2's rules. A range is taken out only where that can't change what's drawn after it: it sets no graphics state outside a `q`…`Q` of its own; outside a text object its `q`s and `Q`s balance, and its `BT`s and `ET`s; inside one it stays inside, its `q`s and `Q`s balance, and it moves no line, and no text shown after it follows it before a line moves or a text object begins; outside one, where it shows text, moves a line or holds a text object, no text is shown after it outside a text object, nor, where it moves a line or holds one, a line moved there, before one begins, as PDFium shows text outside them too; it shows no text while the text rendering mode may add it to the clip, which lasts past its text object, but in a text object of its own inside a `q`…`Q` of its own; it starts and ends outside a path being built, a token, a comment and an operator's operands; and marked content it opens may be closed by a later range, none kept between them, but optional content's ends stay together. Otherwise it's refused (`SpliceError`). Its tokens are read by PDFium's rules under the caller's `Limits`, so a range is judged by the reading those name, an inline image's DCT and CCITTFax data ended by the stand-in or decoded. And what it gives is read again, and refused unless every token kept reads as it did, an inline image's data and what PDFium keeps of it among it, as a token's reading may depend on what's after it: a `BI` with a keyword where its dictionary's key should be, which begins no image, or an inline image whose end is found past it (ASCIIHex data's `>` with no `EI` after it, Flate data whose header asks for a preset dictionary, DCT and CCITTFax data a decoder reads past `EI`). `splice_each` takes out as many groups of ranges as can be (`Spliced`): all together, or those it takes alone, together; content it can't read is an error, not groups refused. `without_keys` writes a marked range's property list again without some of its keys, each entry with the spaces and tabs before it on its line, every other byte as written, its entries found as PDFium reads a dictionary, the list a token of the content read from its start, where what's left reads as the list without them and the content as it did but for the list (`Rewrite`). `Spliced::streams` makes those lists in what's kept of the content they were read from, another of another length refused, and, as lists that each read as they did alone may read otherwise together, or with what's taken out, reads what that gives again, refused unless it reads as it did, each list as it's now written; two lists written again of one list are refused, one given twice made once.
- **Caps, and errors that say where.** It reads under `Limits`: operands before an operator, how deep arrays and dictionaries nest, how many values an operand read holds, an inline image's data, what finding inline images' ends may cost in a reading (`image_ends`: what decoding their data gives, or, of a JPEG decoded with the `image-ends` feature, holds, counted before it's decoded, the data decoded in vain where an end comes to nothing, and what's read in vain past an end looking for `EI`, each place no `EI` was found from remembered, so a deflate bomb, or content of many images read again from inside each other's data, stops with an error, where PDFium reads on), a page's streams joined, and how far a color space is counted (`color`, pdf-color's `Limits`: past one a branch of it doesn't load, which is no error). A string, array, dictionary or inline image that doesn't end, one past a cap, or arrays and dictionaries nested deeper than PDFium reads them, 64 levels, where it reads what's deeper as no object, is an `Error` with where it starts, and nothing comes after it. It never panics, whatever the bytes, and every token moves it on; what's open is kept on the heap, however deep.
- **Where ISO 32000-2 reads it otherwise.** Read by PDFium's rules, content can mean something else by ISO's: a word of digits, signs and points that's a number to PDFium and a keyword to ISO, or a number past what's read, an integer past the 32 bits PDFium reads or a real past an `f32`; a hex string with a byte that's no hex digit; a name with a `#` that escapes nothing, or NUL; a literal string with a CR written in it, which PDFium reads as written and ISO as LF; a number or a name longer than the 255 bytes PDFium reads of a word, or a string longer than the 32,767 bytes it reads of one; a closer with nothing to close, or a brace; an array or a dictionary PDFium ends before ISO would, at a `[` inside an array, outside any dictionary, which opens none, or a dictionary that's none; inside an array or a dictionary, a word that's no object, a key that's no name, or a key with no value; in an inline image's dictionary, a word that's no object as a value, which takes its key out, and an `ID` as one, past which PDFium reads the dictionary on; an inline image's dictionary that an object where a key should be ends, and a `BI` that a keyword there makes no image; an inline image's key with a `#` escape, which ISO decodes and PDFium doesn't, or written both abbreviated and in full where PDFium reads the full name's value and ISO the abbreviation's; a string at any depth, an inline image's data, or a comment that reads a token as comment, running from one of a page's streams into the next, where ISO lets them divide only between its tokens; operands at the end that no operator takes; and an inline image whose length ends its data elsewhere than it's found, whose `ID` has no white-space after it, or with tokens before its `EI`. Each is a `fault::Fault`, which names its clause and whether it's a "shall", told with where it is to a `fault::Sink` the caller gives: `with_sink` on the tokens or the operations, and `object_with` for what's inside an array or a dictionary, read when asked. What's read is the same through any sink. The sink is a type parameter, `()` unless one's given, which wants no faults, so a reader that doesn't ask for them pays for none. One reading isn't told: 0x80 and 0xFF, white-space to PDFium and regular bytes to ISO (§7.2.3), outside a string, a comment or an inline image's data (but as the byte after `ID`).

## The `image-ends` feature

Off by default. With it, a reading that asks for it (`limits.coded_ends = CodedEnds::Decoded`) decodes an inline image's DCT data on [zune-jpeg](https://crates.io/crates/zune-jpeg), and its CCITTFax data on [hayro-ccitt](https://crates.io/crates/hayro-ccitt), to find where it ends as PDFium's decoders do (above), and what's decoded isn't kept. A reading that doesn't ask finds the ends by the stand-in, as without the feature, so turning it on, in this crate or any other built beside it, changes nothing such a reading gives. PDFium's ends are those of a build with libjpeg-turbo as its JPEG decoder, as the build the crate is held to has it, not its Rust one, which says nothing of where it stopped. Where they part from PDFium's decoders: a JPEG of one scan whose last bits libjpeg-turbo's reader holds before it runs into the marker after them, where it stops short of the marker, zune-jpeg saying nothing of where the last bits end; and, on damaged data, a JPEG with no end of image after its coded data, or cut short, which zune-jpeg reads on through to the next marker, where libjpeg-turbo stops at the bits its last row needed; a JPEG of 12-bit samples, whose header zune-jpeg doesn't read; and fax data hayro-ccitt can't decode, where PDFium's decoder reads on as it can. Fax data is given to hayro-ccitt a window of what follows at a time, from 4 KiB, doubled while it runs into the window's end, so data it can't decode, as it says nothing of how far it read, counts as read to its window's end against `Limits::image_ends`, not to the content's end. A fault counts the data on to its filter's own end of data where the decoder ends it sooner, as ISO 32000-2 does: fax data's end-of-block pattern, a JPEG's end of image. The feature needs Rust 1.87, where the crate needs 1.85. zune-jpeg is built without its SIMD features (`x86`, `neon`), which hold all its `unsafe`, so it builds with `unsafe_code` forbidden, as hayro-ccitt does always; a crate built beside this one that turns those features on turns them on here too, as Cargo's features are additive.

## An example

```rust
use pdf_content_streams::{
    Balance, Join, Limits, Operator, Pos, Properties, ResCx, State, Tok, balance, marked, name,
    object,
};
use pdf_content_streams::pdf_objects::Object;

// A page's two streams, joined as they're read.
let mut join = Join::new(&Limits::DEFAULT);
join.push(b"q /Span <</MCID 0>> BDC (Hel").unwrap();
join.push(b"lo) Tj EMC Q").unwrap();
let page = join.finish();

let tokens: Vec<_> = page
    .tokens(&ResCx::none(), &Limits::DEFAULT)
    .collect::<Result<_, _>>()
    .unwrap();
assert_eq!(tokens[0], (0..1, Tok::Op(b"q")));

// Operands are their bytes as written, read when asked.
let (_, Tok::Operand(tag)) = tokens[1] else { panic!() };
assert_eq!(name(tag).as_deref(), Some(&b"Span"[..]));
let (_, Tok::Operand(props)) = tokens[2] else { panic!() };
let mcid = object(props, &Limits::DEFAULT).unwrap();
let mcid = mcid.as_dict().and_then(|d| d.get(b"MCID"));
assert_eq!(mcid.and_then(Object::as_integer), Some(0));

// The string runs from the first stream into the second, as in PDFium.
let (string, _) = tokens[4].clone();
let span = page.span(string);
assert_eq!(span.start, Pos { stream: 0, at: 24 });
assert_eq!(span.end, Pos { stream: 1, at: 3 });
assert_eq!(span.to_string(), "stream 0 byte 24 to stream 1 byte 3");

// Or each operation, with the operands before it.
let ops: Vec<_> = page
    .operations(&ResCx::none(), &Limits::DEFAULT)
    .collect::<Result<_, _>>()
    .unwrap();
let names: Vec<_> = ops.iter().map(|op| op.name()).collect();
assert_eq!(names, [&b"q"[..], b"BDC", b"Tj", b"EMC", b"Q"]);
// Operand 0 is the last, as PDFium takes them.
let props = ops[1].arg(0).unwrap();
assert!(props.is_dict());
assert_eq!(ops[1].arg(1).unwrap().name().as_deref(), Some(&b"Span"[..]));
assert_eq!(page.span(ops[2].range()).start, Pos { stream: 0, at: 24 });

// Each operator typed, and where it may be used: `Tj` in a text object
// alone.
assert_eq!(ops[2].operator(), Operator::Show);
assert_eq!(State::ContentStream.step(&ops[1]), Some(State::ContentStream));
assert_eq!(State::ContentStream.step(&ops[2]), None);

// Its `q`/`Q` balance, and its marked content, from one stream into the
// next.
let res = ResCx::none();
assert_eq!(balance(&page, &res, &Limits::DEFAULT).unwrap(), Balance::default());
let props = Properties::default();
let found = marked(&page, &props, &res, &Limits::DEFAULT).unwrap();
assert_eq!(found[0].tag, b"Span");
assert_eq!(found[0].span.to_string(), "stream 0 byte 2 to stream 1 byte 10");
```

And content written, its resources named at the end, clear of what the page's resources bind:

```rust
use pdf_content_streams::pdf_objects::{Object, ObjectId, dict};
use pdf_content_streams::{ContentWriter, Res, Reserved};

let font = Res::dict(dict! { "Type" => "Font", "Subtype" => "Type1", "BaseFont" => "Helvetica" });
let mut w = ContentWriter::new();
w.begin_text();
w.font(font.clone(), 12.0);
w.text_move(72.0, 700.0);
w.show(b"Hello, (world)");
w.end_text();
let (content, needs) = w.named(&Reserved::default());
let name = String::from_utf8_lossy(&needs.0[0].name).into_owned();
let want = format!("BT\n/{name} 12 Tf\n72 700 Td\n(Hello, \\(world\\)) Tj\nET\n");
assert_eq!(content, want.as_bytes());

// A page whose resources bind that name to another font, object 1: the
// next name up.
let objects = [Object::from(dict! { "Type" => "Font", "BaseFont" => "Courier" })];
let resolve = |id: ObjectId| objects.get((id.0 as usize).checked_sub(1)?);
let resources = Object::from(dict! { "Font" => dict! { name.as_str() => Object::reference(1) } });
let (_, renamed) = w.named(&Reserved::read(&resolve, Some(&resources)));
assert_ne!(renamed.0[0].name, needs.0[0].name);
assert_eq!(renamed.0[0].res, font);
```

## What isn't here

- **A file.** Finding a page's streams, decoding them and reading its resources are a reader's, which gives this crate the streams' bytes, the resources dictionary whose color spaces their inline images are drawn in, with a resolver for what it refers to (`ResCx::read`), and the property lists its marked content names.
- **Binding a writer's resources.** Putting what written content needs into the resources dictionary it goes with, and its objects into a file, is the caller's: the writer names each need and gives its resource.
- **An inline image's pixels.** Flate and LZW data, and, where a reading asks for it, DCT and CCITTFax data, is decoded only to find where it ends, and what's decoded isn't kept.
