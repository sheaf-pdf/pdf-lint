# Changelog

## 0.1.0 (unreleased)

- **Tokens.** `tokens(bytes, &ResCx, &Limits)` gives a content stream's tokens in order, a `Tokens` iterator (fused, `Clone`, `Send` and `Sync`) of each token's range and its `Tok`: `Op`, an operator, any word that isn't a number, `true`, `false` or `null`; `Operand`, an operand's bytes as written, a number, a name, a string, an array or a dictionary with all it holds, or a closing delimiter with nothing to close; or `InlineImage`, `BI` to `EI`, one token, with its data's range. Between them is only white-space and comments, and after an error nothing comes. Tokens end where PDFium's `CPDF_StreamParser` ends them: at white-space and delimiters, a word of digits, signs and points a number, strings nested, and an array or a dictionary one token.
- **On pdf-tokenizer.** Content's tokens are pdf-tokenizer's (0.1.1), read by its PDFium rules (`Pdfium`), where they were a scanner of this crate's own: white-space and comments passed over without a token each (its `next_significant`), an array or a dictionary passed over to the closer that balances its opener by its `skim`, which reads only the tokens that open or close one and a string that doesn't close (what's open kept on the heap, under the cap on depth, as before), operands, an image's dictionary and what a page's joins divide read from its tokens, and its byte classes, its number words' kinds and ISO 32000-2's number test (`decode::number`, `decode::integer`) its own. A number operand reads by pdf-tokenizer's `decode` as ISO writes it, a literal string's bytes by `decode::literal` and a hex string's by `decode::pdfium::hex`, as before; a name's escapes as before. An inline image's data is still found in its bytes where its filter ends it, or at an `EI` between white-space, each marker (`EI`, ASCIIHex's `>`, a JPEG's end of image) searched for with memchr, its default features off. The same tokens, operations, operands, errors and faults as the scanner gave, but in two places, each where the scanner read otherwise than PDFium: 0x80 and 0xFF are white-space, as PDFium reads them (it fills `1 2 3 4<80>re f`'s rectangle, takes `/F0<80>10 Tf`'s font `F0`, and takes either after `ID` as the one white-space byte before an inline image's data), where the scanner read them as regular bytes, part of a word or a name; they aren't told as faults, and as the byte after `ID` they're told as `AfterId`, which needs ISO's white-space. And a word of more digits than 64 bits hold with a sign after them, such as `99999999999999999999--5`, reads as no object, as `--5` does, ISO 32000-2 writing no such number (§7.3.3), where it read as the largest integer of its sign (Rust's integer parse stops at the overflow, before the sign).
- **Inline images' dictionaries as PDFium structures them** (its `Handle_BeginImage`), where they were read to `ID` with what isn't a name where a key should be passed over: an object that's no name there (a number, a string, an array, a dictionary, `true`, `false`, `null`, a closer or a brace) ends the dictionary, and the data is read from after it, one white-space byte passed over, as from after `ID`; a keyword other than `ID` there makes the `BI` no image but an operator of its own (`Tok::Op`), what's after it read as content, the dictionary's tokens among it; and a value PDFium reads as no object, a keyword (`ID` among them), a closer or a brace, takes its key out, so an `ID` there no longer ends the dictionary. As PDFium 7881 and 8076 alike read them: `BI /W 1 /H 1 foo /BPC 8 /CS /G ID a EI ...` is no image, `BI 7 /W 1 /H 1 /BPC 8 /CS /G ID (x EI 0 0 m 9 9 l S) EI 5 5 m 7 7 l S` an image of no data and one path after it, not two, `BI /W 1 /H 1 /BPC 8 /CS foo ID abc EI` an image of one byte, not three, and `BI /W 1 /H 1 /BPC 8 /CS ID x EI` no image. An operation named `BI` may so be no image (`inline_image` none), with the operands before it, as PDFium clears them after it, and `State::step` takes it as allowed where an image may begin, content staying where it was, as nothing is drawn. Faults: `DictEnd`, new, where an object ends an image's dictionary, which was told as `Key`; `LoneBi`, new, from the `BI` to the keyword, told as reading passes the keyword, which was told as `Keyword`; `NoValue` for a key whose value is `ID`, as before, its doc saying PDFium reads on past it. A lone `BI`'s dictionary's tokens are content, their faults told as content's. A `BI` among them, a value there, is lone with the same keyword, its dictionary not read on to it again, so content of many such reads in one pass. Two tests that read the earlier way are changed: an image whose dictionary starts `BI 7` has its data from after the `7`, and an image's dictionary's faults are those of the same dictionary with the `7` moved after its `ID`, where it ends it (`DictEnd`); and the test of a sink that wants none reads a lone `BI` and an ended dictionary where it read the `7`.
- **Operands, names and strings as PDFium's content parser reads them.** `Operand::number`, new, reads an operand as PDFium reads a number (`GetNumber`), an `f32`: a number word by its first 255 bytes, the most of a word PDFium keeps, by pdf-tokenizer's `decode::pdfium::number` (a whole number in 32 bits, unsigned without a sign and signed with one, 0 past them; a real the decimal it starts with), and 0 for what isn't one; an array's elements alike. `name`, and so `Operand::name`, `Operation::resource`, `names_used`, `marked`'s tags and an inline image's values, reads a name as PDFium does (`PDF_NameDecode`), where it read a `#` as an escape only before two hex digits: a `#` with two bytes after it stands for the byte they make, one that's no hex digit read as 0, so `/F#3G` is `F0` and `/#zz` NUL, as PDFium 7881 and 8076 find `Tf`'s font `F0` by `/F#3G`; and a name longer than 255 bytes, its `/` among them, as its first 255. `object` reads a literal string's CR or CR LF written in it as written, where it read LF as ISO 32000-2 does (§7.3.4.2), as PDFium shows `(a\rb\r\nc) Tj`'s text; and a literal's or a hex string's first 32,767 bytes, read, as PDFium keeps of one; its numbers as before, at 64 bits. An inline image's `/W`, `/H` and `/BPC` are read as PDFium reads an integer from each (`GetIntegerFor`: a real cut to its whole part, `true` 1, what's no number 0, an unsigned one past `i32` wrapped), held in 32 bits, the size counted as PDFium counts it, where they were read as ISO writes a number, a non-negative one under 2^32: `/W true` sizes one pixel, `/W -1` or a size past 32 bits none; and an image whose size PDFium can't count, filtered or not, has its data read on to the next `EI` from its start, as PDFium reads no data of it, where a filter's end was sought (`BI /W -1 ... /F /AHx ID 41 EI 1 1 m 2 2 l S 42> EI` draws that path, PDFium 7881 and 8076 alike). PDFium 7881 counts a row of 2^32 − 7 bits or more as past 32 bits, and 8076, followed here, doesn't. Its color space's name is looked up as PDFium decodes it (`/C#5G` is `CP`). `InlineImage::length` reads `/L` as before, as ISO 32000-2 writes a number. Faults: `StringCr`, new, a literal string with a CR written in it; `Long`, new, a number or a name longer than 255 bytes, or a string whose bytes, read, are more than 32,767; `OutOfRange` told too for an integer outside the 32 bits PDFium reads (`4294967296`, `+2147483648`) and a real past an `f32`, which `number` reads as 0 and as infinite; `Name`'s doc saying how PDFium reads its `#`. Four tests that read the earlier way are changed: `name(b"/#zz")` is NUL; a string operand's CR LF is read as written; an 8 MiB hex string inside 500 arrays reads its first 32,767 bytes; and the integers 9223372036854775807 and -9223372036854775808 are past the numbers read here, and a real of 402 bytes longer than PDFium reads too.
- **Inline images** ended by PDFium's `ReadInlineStream` rules, by the first filter: unfiltered, by the data's exact size (`/W`, `/H`, `/BPC` and its color space's components, rows padded to a byte; an image mask's one bit of one component; a name the resources don't have read as none); `/AHx` to its `>`, `/A85` past the first byte that's none of its digits or white-space, and a `>` after it, and `/RL` to its end-of-data byte, as PDFium's decoders end them; then on to the next `EI`, its tokens read as PDFium reads them. A filter PDFium can't decode, one of those that finds no end, or an image no size counts reads on from its data's start to the next `EI`. `/L` and `/Length` aren't read, as PDFium reads neither. `/Fl`, `/LZW`, `/CCF` and `/DCT`, which PDFium decodes to find their end, aren't decoded: a JPEG ends at its end of image, the others, or a JPEG with none, at the first `EI` with white-space before it and white-space, a delimiter or the end after. The dictionary is read as PDFium structures it (above): a key matched as written, its `#` escapes not decoded; a value's decoded, and an abbreviated name read as the full one, a color space looked up by it (`/I` as `/Indexed`); of a key written both abbreviated and in full, the abbreviation's value, unless the full name's is an abbreviated name, which PDFium sets over it; the filter a name, or a string's bytes, naming one, and `null`, a dictionary or an empty array none. Each filter's end, a JPEG's end of image, ASCIIHex's `>`, the byte ASCII85 data stops at and RunLength's end-of-data byte, is searched for once for the images that share it, or that find none (a RunLength walk that finds none remembers each place it passed, a bit for each byte of the content), so content of many images whose data doesn't end is read in time that grows with its length, not with its square. `ResCx` gives the components of the color spaces the resources name, under their names decoded as PDFium decodes them (`ResCx::new`, `ResCx::none`), and `family_components` counts a family as the lexer does.
- **Operations.** `operations(bytes, &ResCx, &Limits)` and `Concat::operations` give a content stream's operations in order, an `Operations` iterator (fused, `Clone`, `Send` and `Sync`) of `Operation`s, its tokens grouped: each operator, or inline image, with the operands since the last, and after an error nothing. An operation's operands' ranges are held in the item (tinyvec's `TinyVec`), sixteen inline, as many as PDFium keeps, so an operation of no more allocates nothing; more spill to the heap, every operand kept up to `Limits::operands`, past which is the operand cap's error, where the first past it starts. Operands at the end, which no operator takes, are no operation. `Operation`: `name`, the operator as written (`BI` for an inline image, and for a `BI` that begins none); `at`, where the operator is, or the image, `BI` to `EI`; `range`, from its first operand; `operands`, in order, an exact-size iterator; `arg(i)`, operand `i` from the last, as PDFium takes them, none past the first for any `i`; and `inline_image`, none for a `BI` that begins no image. Its `Debug` shows the operation, not the content.
- **Inline images as operations.** `InlineImage`: `at`, `dict` (what's between `BI` and `ID`, or the object that ends it), `data`, `entry(key)`, the value under a key, as written, as PDFium reads the dictionary (either spelling of a key 8.9.7 abbreviates finding the one value; a key matched as written; of a key written twice, the last; a key a value PDFium reads as no object takes out, none); and `length`, its `/L` or `/Length` where that's a length, `/L`'s where both are written.
- **Operands as written.** `Operand`, an operand's bytes and where they are (`bytes`, `range`), `Copy`: `name` and `object` read it as the functions of those names do, and `object_with` with a sink; `number`, as PDFium reads a number from it; `elements`, an array's elements as written, each an `Operand` where it is, found as they're asked for (`Elements`), none for what isn't an array; and what kind it is: `is_number` (a word of digits, signs and points, as PDFium tells a number), `is_name`, `is_string`, `is_array`, `is_dict`, from how it starts.
- **Operands.** `name` decodes a name operand's `#` escapes as PDFium does, borrowing it when there are none (above); `object(operand, &Limits)` reads an operand as a pdf-objects `Object`, unplaced: an integer or a real as ISO 32000-2 writes one, read by pdf-tokenizer's `decode`, one past 64 bits as pdf-objects reads it (the nearest integer that fits, the largest finite real of its sign), `true`, `false`, `null`, a name decoded, a string's bytes in its `Form`, read as PDFium reads them (above), and arrays and dictionaries read in one pass, a dictionary keeping every entry, as `Dict` does, and passing over an entry whose key isn't a name; none for what isn't an object, one nested deeper than `Limits::depth`, or one of more values than `Limits::values`. It reads a token's bytes as well as an `Operand`'s. pdf-objects is re-exported (`pdf_content_streams::pdf_objects`).
- **A page as one.** `Concat` joins streams with a space between each, as PDFium joins a page's, one stream borrowed as it is: `bytes`, `stream_count`, `stream`, `range`, `pos` and `offset` (a joined offset to a `Pos`, a stream and a place in it, and back), `span` and `offsets` (a range to a `SpanAcross` and back), and `tokens`. `Join` joins them as they're read, under `Limits::content`, and under 4 GiB whatever it says, past which a `Pos` can't count: `push`, `push_with`, which hands a decoder the joined bytes to append to and the room left (`room`), cutting back to where they were, the space too, when it fails or writes past its room, and `finish`. A stream pushed, an empty one too, is the next stream, so a `Pos`'s stream is the index of the stream given. Past the cap is `TooLarge`; `push_with`'s refusal is `Pushed`, the cap's or the decoder's error.
- **Caps and errors.** `Limits` (`#[non_exhaustive]`, set on a copy of `Limits::DEFAULT`): `operands` before an operator (65,536), `depth` of arrays and dictionaries (512, PDFium's; reading an operand nests on the stack a level for each, so a far higher cap needs a stack to match), `values` an operand read as an object may hold (2^25, as pdf-objects'), `inline_image`'s data (64 MiB), and a page's `content` joined (256 MiB). `Error`, an `ErrorKind` and the offset where what's wrong starts, displayed as the kind and its byte: a string, hex string, array, dictionary or inline image that doesn't end, nesting past the cap, operands past it, an inline image's data past it; and `Marked` and `Emc`, for marked content that doesn't end and an `EMC` that ends none. Derived with thiserror; `ErrorKind` is `#[non_exhaustive]`. Never a panic, whatever the bytes.
- **Faults.** `fault::Sink` and `fault::Fault` (`#[non_exhaustive]`, thiserror, borrowing the content read): where ISO 32000-2 would read content otherwise than it's read here, by PDFium's rules, told with where it is, each fault's doc naming its clause and whether it's a "shall": `Number`, a word of digits, signs and points that ISO doesn't write as a number; `OutOfRange`, an integer outside the 32 bits PDFium reads or a real past an `f32`'s, which `Operand::number` reads as 0 and infinite, and so an integer outside 64 bits or a real past a 64-bit float's, which `object` reads as the nearest that fits;
